# Предметная модель и правила MelodyTrack

С 31.10.2026 по решению пользователя разделены данные, предметные функции и прикладные операции. Неизменяемые записи и `CSharpFunctionalExtensions.Result<T, ErrorList>` сохранены. Карта подтверждённых требований и открытых вопросов — в [покрытии спецификации](../../docs/domain-models.md).

## Границы

- Файлы в корне Domain описывают состояния сущностей: свойства, внутренние конструкторы, начальные значения и простые производные свойства данных.
- `Rules/` содержит чистые функции создания, переходов и расчётов. Функция получает состояние и необходимые факты, возвращает новую запись или типизированную ошибку. Она не проверяет полномочия вызывающего сотрудника.
- Проверки ролей, области доступа и допустимого месяца исправления находятся в `Application/Authorization.cs` и `Application/Operations/`.
- `Application/AppointmentAccounting.cs` координирует результат занятия, источник оплаты и изменения финансовых фактов. `Application/SeriesOperations.cs` координирует подтверждённое восстановление занятия с заменой компенсационной встречи.
- Объекты значений сохраняют локальную валидацию и операции над самим значением: `Money`, `TimeInterval`, `LessonDuration`, `SequenceNumber`, `StartHour`, `WeeklyRule`, `PersonName`, `ExternalLink`, `YouTubeClip`, конфигурации и цели упражнения.

Запись не имеет методов `Complete`, `Approve`, `Archive`, `Extend` или `ChangeStatus`. Некоторые функции правил и прикладных операций объявлены как C# extension methods: запись `appointment.Complete(...)` в вызывающем коде обращается к отдельной статической функции, а не к методу сущности. Для явного указания слоя можно использовать статический вызов:

```csharp
// Предметное правило: состояние и время, без роли.
var result = AppointmentRules.Complete(appointment, now);

// Прикладная граница: полномочия и календарный месяц, затем предметное правило.
var authorizedResult = AppointmentOperations.Complete(appointment, role, now);
```

API должен входить через Application. Публичность предметной функции не даёт пользователю права вызывать её через HTTP. Внешний код не может менять свойства сущностей: конструкторы и изменяемые через `with` свойства доступны только внутри Domain. Application вызывает функции правил и не получает доступ к внутренним setters. Нет `InternalsVisibleTo`, методов-обёрток в моделях или второй реализации переходов.

## Время и исходные факты

БД, HTTP, Quartz, криптография и текущие часы не входят в Domain. Время передаётся явно. Конкретные моменты нормализуются в UTC; календарные даты и месяцы относятся к Europe/Moscow. Интервалы — `[начало, конец)`, скрытых буферов нет. Ошибки непустые, неизменяемые, типизированные и при необходимости привязаны к полю.

Правила получают актуальные срезы истории и зависимостей. Application должна читать их в согласованной транзакции, повторять необходимые проверки и сохранять все связанные изменения с аудитом, задачами и уведомлениями. Подготовка изменённых записей не означает их транзакционное сохранение или доставку сообщения.

`AppointmentAccountingChange` содержит занятие и только изменяемые строки списаний. При снятии результата строка обновляется по прежнему ID с признаком отмены, а не добавляется дубликатом. Повторная отметка уже записанного результата не переоценивает прежний источник. Исправление одной встречи не перераспределяет покрытия остальных.

Историческое использование абонемента сохраняет запрет отменить покупку после снятия результата. Продление сохраняет уже предоставленные интервалы и не уменьшается после удаления отпуска. Исторический прогресс исключённых тем не удаляется; добавление темы не снимает завершение прохождения. Эти правила не являются проверками доступа.

## Проверки и последующая работа

Существующие тестовые сценарии переведены на фабрики правил и прикладные операции. Проект `MelodyTrack.Rewrite.Domain.Tests` ссылается на Domain и Application: предметные сценарии проверяют чистые функции, а сценарии ролей и доступа — прикладную границу. Производственная зависимость остаётся только `Application → Domain`.

В рамках этого рефакторинга сборка, тесты, линтеры и форматтеры не запускались. Проверка исполнимости ожидает отдельной команды пользователя. Прикладные операции пока готовят изменения в памяти; загрузка/сохранение, транзакции, HTTP-контракты, восстановление состояний для переноса и доставка уведомлений остаются следующими задачами. Открытые предметные вопросы перечислены в карте покрытия и не разрешались этим рефакторингом.

Для первого блока клиентов уже добавлены `ClientRules.Restore` и `ClientContactRules.Restore`, исходные дата создания/флаг лида и представление неизвестного источника. Новая фабрика клиента получает дату явно, а создание/редактирование карточки сохраняет обязательность источника. Это чистое восстановление моделей; SQL-схема, защита контактов и оставшаяся работа импорта описаны в [хранении клиентов](../../docs/client-storage.md).

## Накопление ошибок

`ErrorListBuilder` собирает независимые ошибки через `Add(error, field)`, `AddIf(condition, error, field)`, `AddRange(issues)` и `Add(check)` для `UnitResult<ErrorList>`. `ToResult()` возвращает успех для пустого билдера или отказ с неизменяемым непустым снимком. Проверять размер коллекции в вызывающем коде не требуется; последующие добавления в билдер не меняют ранее возвращённый результат.

`ErrorList.Single(error, field)` предназначен для немедленного отказа с одной причиной. Фабрики `ErrorList.From` и `ErrorList.Combine` удалены; `Validation.Collect` объединяет проверки через тот же билдер. Создание снимка из билдера требует первый элемент отдельно от остальных, поэтому пустой `ErrorList` через этот путь не создаётся.

Добавлены сценарии `ErrorListBuilderTests`: пустой результат, условное добавление, объединение успешных/неуспешных проверок, сохранение порядка, путей и повторяющихся ошибок, независимость снимка от последующих изменений. В рамках этой порции сборка и тесты не запускались.
