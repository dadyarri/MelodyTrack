# Защита клиентских данных

Реализована защита значений: `PersonalDataProtector`, `ClientDataProtection` и отдельный `LegacyPersonalDataReader`. Они используются [первым пакетом импорта](client-import.md), прикладной CRUD ещё не реализован. По прямому запросу пользователя выполнены сборка и фокусные проверки, включая защиту данных и конфигурацию API; результаты и блокер проверки исходных зашифрованных данных описаны в отчёте импорта.

## Новое хранилище

`PersonalDataProtector` использует библиотечный `System.Security.Cryptography.AesGcm`: AES-256-GCM, случайный nonce длиной 12 байт и tag длиной 16 байт. Новый nonce создаётся для каждой операции, включая повторную запись того же текста. Требования к nonce и associated data приведены в [документации .NET](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.aesgcm.encrypt?view=net-10.0).

Сохраняемый формат:

```text
mtpii:1:<key-version>:<nonce-base64>:<ciphertext-base64>:<tag-base64>
```

Версия `1` относится к формату, а `key-version` — к ключу. Версии ключей регистрозависимы, состоят из ASCII букв/цифр, дефиса и подчёркивания. Associated data — UTF-8 строка `mtpii:1:<key-version>:<context>`. Подмена версии, контекста или защищённых байтов приводит к отказу чтения. Чтение открытого текста и старого `enc:` в новом хранилище запрещено. Никакого автоматического возврата непроверенного значения при ошибке нет.

`ClientDataProtection` формирует контексты из новых целевых ID; UUID записывается в формате `N`, строчными hex-цифрами:

| Поле SQL | Контекст |
| --- | --- |
| `clients.protected_notes` | `clients/<client-id>/notes` |
| `client_contacts.protected_value` | `clients/<client-id>/contacts/<contact-id>/value` |
| `client_contacts.protected_comment` | `clients/<client-id>/contacts/<contact-id>/comment` |

Копирование шифротекста между владельцами, контактами и полями не даёт читаемого значения. Разрешённый перенос контакта к другому владельцу потребует расшифровки в прежнем контексте и повторной защиты в новом. Названия контекстов — часть формата хранения; их изменение требует преобразования данных.

Пробелы, переносы и Unicode сохраняются без нормализации. Некорректная UTF-16 строка отклоняется, а не исправляется заменой символов. SQL NULL остаётся NULL; непустой шифротекст создаётся даже для пустой исходной строки. Шифрование не определяет допустимость контакта: предметные проверки остаются в Rules.

Ошибки конфигурации и чтения имеют общие сообщения без ключей, значений и вложенных исключений с исходными данными. Временные массивы открытого текста и загруженные байтовые ключи обнуляются. Неизменяемые строки .NET и конфигурационные строки таким способом стереть нельзя; код не обещает полного удаления секрета из памяти процесса.

## Конфигурация API

API вызывает `AddPersonalDataProtection()`. Настройки `PersonalDataProtectionOptions` проверяются при старте host; пустая или некорректная конфигурация не позволяет начать обслуживать запросы. Защита и контексты клиента регистрируются как singleton, DI освобождает загруженные ключи вместе с host. Ключи источника и `LegacyPersonalDataReader` в API не регистрируются.

| Ключ конфигурации | Значение |
| --- | --- |
| `PersonalData:CurrentKeyVersion` | Текущая версия, например `v1` |
| `PersonalData:Keys:<version>` | Base64-представление 32 криптографически случайных байт |

Для стандартного провайдера переменных среды имена имеют вид `PersonalData__CurrentKeyVersion` и `PersonalData__Keys__v1`. Реальные значения в репозитории отсутствуют; `appsettings.json` не содержит ключа по умолчанию. В development используется внешняя секретная конфигурация, в production — контролируемая серверная конфигурация секретов. ASP.NET Core поддерживает [раздельное хранение секретов](https://learn.microsoft.com/en-us/aspnet/core/security/app-secrets?view=aspnetcore-10.0); Secret Manager предназначен для development и сам не шифрует значения.

Старый строковый master key не является новым 256-битным Base64-ключом. Для новой БД создаётся отдельный ключ. Init не требует этих настроек для создания схемы; явный режим импорта клиентов требует и исходные, и целевые ключи.

Для смены ключа добавляют новую версию и меняют `CurrentKeyVersion`, сохраняя прежние версии, затем перезапускают API. Новые записи используют новый ключ; прежние читаются по своей версии. Массовое повторное шифрование и его контроль ещё не реализованы. Удалять старый ключ до преобразования всех зависимых данных и учёта резервных копий нельзя. Резервирование ключей относится к D-410.

## Чтение источника

`LegacyPersonalDataReader` воспроизводит формат референса `1636c2c4dabdd33420209cfd6617cc3c82fe2433`:

```text
enc:<key-version>:<nonce-base64>:<ciphertext-base64>:<tag-base64>
key = SHA256(UTF8("melodytrack:pii:" + original-master-key))
```

Это прежние AES-GCM без associated data, nonce 12 байт и tag 16 байт. Reader принимает все нужные версии исходных строковых master key отдельно от новых ключей; прежние допустимые Unicode-метки версий также читаются. Точное значение без префикса `enc:` возвращается как исходный открытый текст, включая NULL, пустые строки и пробелы. Такое поведение необходимо для старых EF-конвертеров и незашифрованной истории и не разрешено при чтении нового хранилища.

Если `enc:` повреждён, ключ неизвестен или tag не прошёл проверку, reader бросает `CryptographicException` с общим сообщением. Импортёр переводит это в `source_decryption_failed` для ручного разбора по D-399 и откатывает весь объект клиента с его новыми соответствиями ID. Нельзя заменить такое значение пустым контактом или записать шифротекст в качестве контакта.

Порядок переноса: прочитать источник → расшифровать старым ключом → восстановить модель с предметными проверками и целевыми ID → защитить поля в целевом контексте → записать в транзакции с соответствиями ID и сверить. Простое копирование старого `enc:` в `protected_*` не допускается. Reader не предоставляет записи в старом формате.

## Подготовленные сценарии

Добавлены и успешно выполнены тесты независимых фиксированных шифротекстов нового и старого форматов, точного восстановления Unicode/пробелов, NULL/пустых строк, повторной защиты, смены ключей, подмены полей/владельцев, повреждённых значений, безопасных ошибок и освобождения ключей. Отдельные тесты host проверяют регистрацию и отказ при отсутствии ключей. Проверка настоящего OldDatabase пока не прошла: недоступны исходные ключи.

Импорт использует read-only соединение к источнику, карту ID и отчёт. Нормализация для сравнения, blind index и прикладные запросы хранения остаются следующими шагами. Шифрование не заменяет прикладные полномочия, аудит и транзакционные проверки.
