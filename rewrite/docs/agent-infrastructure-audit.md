## Политика источников уже существует

[README спецификации](../../specification/README.md) прямо различает
подтверждённое, наследуемое, направление roadmap, предложение и открытый вопрос.
Текст документа и реализованная старая функция сами по себе не подтверждают
требование v2. При расхождении вопрос фиксируется явно; позднее решение
пользователя определяет целевое поведение. Это существующая политика, а не
новый проект политики для повторного утверждения.

Для работы достаточно применять её последовательно:

1. Явные указания пользователя и подтверждённые решения определяют целевой
   сценарий; связанный рабочий раздел даёт условия и приёмку.
2. Два подтверждённых несовместимых правила требуют решения, если в журнале
   нет явной замены. Просто выбирать более свежий файл нельзя.
3. README/код/тесты определяют фактическую реализацию и её проверенность.
   Ожидаемый результат QA выводится из подтверждённых требований.
4. Историческое правило классифицируется как подтверждённое спецификацией,
   явно сохранённое, неизвестной актуальности, противоречащее новому либо
   отменённое/заменённое. Для вывода нужна ссылка на источник и решение;
   отсутствие в новой спецификации само по себе не отмена.
5. Предложение агента остаётся предложением. Пробел блокирует только зависимую
   часть работы, а не все независимые действия.

## Технические факты и обнаруженные расхождения

- `global.json` фиксирует SDK `11.0.100-rc.3.26522.148`, MTP; локальный
  `Directory.Build.props` — `net11.0`, локальный CPM уже включён.
  Предметная архитектура — C#/Rules/Application/Npgsql/Dapper, не старый EF.
- Api пока host и преобразование Result/Problem Details, без предметных
  маршрутов. Новый frontend, Quartz и большая часть схем ещё не реализованы.
  React/Vite/FSD/Query/Kiota в архитектуре — направление исходного наброска,
  а не доказательство наличия нового frontend и генератора.
- В начале README rewrite остаётся фраза о внешней спецификации со старой F#
  границей. Она устарела после D-455 и commit `7edde10`; текущая
  `specification/architecture.md` уже описывает C#. Это редакционное
  техническое расхождение, не повод снова выбирать язык.
- Модели и тесты абонементов, парных встреч, отпусков и скидок местами
  предшествуют D-420–D-455. Карта моделей прямо предупреждает об этом.
  Их успешный тест не утверждает прежнее поведение как целевое.
- D-391/ARCH-008 требует небольших законченных порций backend с ручным ревью
  пользователя. Это ограничивает автономность реализации, но не требует
  согласования каждой локальной технической детали.
- Актуальные вопросы: BIZ-13 (прогноз без результата), BIZ-25 (повтор долга),
  BIZ-38/39/42/44 (задачи и отпуск), BIZ-27/33 (публичные сведения), вопросы
  матрицы прав. Принятые цена пары, денежная оплата, полный офлайн, скидки и
  наследование прав повторно не открываются. Курсы/ДЗ отложены D-446.
- D-415 закрепляет production commit
  `1636c2c4dabdd33420209cfd6617cc3c82fe2433`; объект доступен в Git.
  D-416 принимает 49 миграций до `Stage14TimedVacations`, PostgreSQL 17.
  Локальная фикстура PG18.6/55 миграций — другой источник, только read-only.
- `data-migration.md` сообщает об успешной проверке одного поля ключом из IDE
  workspace 29.10; `client-import.md` описывает неподходящие launchSettings
  ключи и незавершённый live-импорт 01.11. Это разные свидетельства о разных
  источниках ключей. Не объявлять импорт принятым и не читать секреты
  автоматически. Нужна отдельная разрешённая проверка при возвращении к импорту.

Последние релевантные изменения: `7edde10` синхронизирует спецификацию,
`d55f598` фиксирует клиентскую схему, `7c2b74d` — production и задачи,
`b4c1f74` — решения переноса, `25ba6a7` — первый пакет импорта,
`86e594c` — задание текущего аудита. История использована для происхождения,
а не для автоматического утверждения старых правил.

Каталог текущего запроса содержит большинство родительских skills, но
`melodytrack-verify`, `melodytrack-commit` и системный `review-agent` найдены

конкретным клиентом; их можно прочитать по явному пути. После установки новой
инфраструктуры автоматическое обнаружение следует проверить в новом сеансе.

папки skill: отсутствующих файлов не выявлено. Существующая ссылка на старый

Все перечисленные plugin scopes сохранены без изменений; не создаются
проектные копии и не включается новый внешний сервис. Фактическое поведение

## Доступные инструменты и CI

Фактически объявленные MCP namespaces текущей сессии: `rider`, `cmd_monitor`,
`node_repl`, `codex_apps`. Последний включает GitHub, Google Drive/Gmail,
document control, Sites, Pets, plugin management и другие подключённые сервисы.
Это runtime inventory, а не содержимое `mcp_servers` пользовательского TOML.
Есть native shell/patch, web/imagegen и collaboration. Rider предоставляет
semantic refactoring, build state, debugger и DB tools; наличие DB tools не
разрешает подключаться к исходным/production данным. Binlog MCP не объявлен.

В PATH найдены `python3`, `git`, `rg`, `dotnet`, `gh`, `docker`, `jq`,
`node`, `npm`; fnm найден в `~/.local/share/fnm/fnm`. Видимый Node принадлежит
IDE runtime 24, поэтому команды исходного Web с Node26 запускать через fnm.
Версии/сеть/авторизация/daemon здесь не проверялись.

Родительский `.github/workflows/ci.yml` использует SDK10, старую solution,
compiled xUnit executable lanes, frontend static/security/unit/Chromium/WebKit/
bundle, contract generation, unified image integration и release publication.
Упоминаний rewrite в workflow нет: зелёный CI старого приложения не доказывает
сборку или тесты rewrite. В rewrite отдельного CI до этой задачи нет.

Переиспользуемые инструменты: `scripts/ReleaseTool.cs` и
`scripts/verify-unified-image.sh` родительского проекта, существующие Web
verification scripts, стандартные dotnet/MTP и Git. Они не требуют собственной
LLM-оркестрации. Для rewrite полезна узкая обёртка выбора проверок и компактных
сводок; package generation/release/container workflow заново создавать не нужно.

Большой вывод дают MSBuild diagnostic/binlog, полный MTP прогон и browser/build
lanes старого Web. Для обычной диагностики достаточно exit code, количества
результатов/ошибок, повторяющихся diagnostic IDs и ссылок на полные файлы.
MTP TRX требует установленного report extension; его отсутствие нельзя маскировать
успехом. Структурированный отчёт и full log — разные доказательства: успешная
сборка не заменяет провалившийся тест, а зелёный rerun одного теста не заменяет
полный ещё не выполненный набор.

## Что остаётся за пользователем

Новая политика источников не требует утверждения: она уже задана спецификацией.
Предметные вопросы остаются в существующем реестре, а не копируются сюда.
Рекомендации по внешним skills/config не применяются этой задачей. Отдельное
решение потребуется только при фактическом изменении их области применения,
при возвращении к спорному предметному сценарию или при разрешённой работе
с секретной конфигурацией незавершённого импорта.
