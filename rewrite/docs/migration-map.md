# Карта переноса из production в rewrite

**Изменение требований, разобранное 04.11.2026:** по [ответам заказчика](open-questions.md) сущность абонемента исключается, вся механика курсов откладывается, занятие допускает до двух клиентов, права становятся индивидуально настраиваемыми. Соответствия ниже для абонементов, курсов, участников занятий и прав требуют пересмотра целевой модели; они описывают прежний проект. Исходные покупки, использования, продления, программы и прогресс не разрешено терять. Конкретное представление этих исторических данных пока не определено.

Срез 31.10.2026. Источник — commit `1636c2c4dabdd33420209cfd6617cc3c82fe2433`, PostgreSQL 17, все 49 миграций до `Stage14TimedVacations`, принят по D-415/D-416. [Полная инвентаризация](source-schema.md) содержит 45 EF-таблиц, 327 столбцов, ограничения и внешние ключи, а также 11 таблиц Quartz и историю EF.

Это проект соответствий, а не реализованный импорт. Имена справа — существующие C#-модели; конкретные SQL-таблицы описываются для каждого реализуемого блока отдельно. Добавлены первая миграция клиентов/контактов/источников и пути восстановления их моделей — см. [хранение клиентов](client-storage.md). Остальная предметная схема ещё не реализована. Наличие записи не означает полноту её полей или готовый перенос. Миграции, Init, базы и проверки исполнимости не запускались.

## Обозначения и общие правила

- **Преобразование**: соответствие определено для указанных полей; остаются проектирование хранения, импорт и сверка на копии.
- **Пробел**: существующая модель теряет часть фактов или требует отсутствующие в источнике сведения. До разрешения нельзя считать таблицу перенесённой.
- **Служебное**: данные относятся к инфраструктуре/доступу. Политика переноса или пересоздания выбирается явно; сам этот статус не разрешает удаление.

D-397 задаёт отдельную целевую базу. D-414 задаёт новые UUIDv7 и сохранённую перепривязку всех ссылок. D-399 требует предупреждений для ручного разрешения неожиданных состояний. Предупреждение не заменяет успешный перенос. Неразрешённые строки сохраняются в источнике, а перенос соответствующего блока не отмечается завершённым. Не вводится заранее универсальная постоянная модель исторических исключений.

Полный перечень исходных полей — в инвентаризации. Поля без места в текущей модели перечислены ниже: им требуется предметное/инфраструктурное хранение либо отдельное согласованное решение. Сохранение старой БД необходимо для пробного переноса и отката, но само по себе не означает, что новая система умеет читать её историю.

## Идентификаторы, связи и порядок загрузки

Предложение хранения соответствий для реализации D-414: миграционный журнал с ключом `(источник, таблица/тип, старый ID, целевая роль записи)` и новым UUIDv7. Это техническое состояние одного переноса, не второй формат ID в предметной модели. UUID генерируется один раз и повторно читается при продолжении. При разбиении записи роль отличает, например, сотрудника от credentials, а также Contact.Phone от Contact.Email. При объединении таблиц старые Id различаются исходным типом: ClientVacations и UserVacations могут иметь одинаковые байты.

Для контактов ключ дочерней записи включает владельца-клиента, Id исходной строки и имя поля. `Clients.ContactsId` не уникален: один ClientContacts может принадлежать нескольким клиентам, и нельзя произвольно отдать контакт одному из них. Для нормализованного совпадения телефонов/email у разных клиентов не вводится глобальная уникальность.

Сначала создаётся соответствие для всех переносимых строк, затем сущности и FK. Циклы VacationRequest ↔ Vacation разрешаются предварительным выделением ID и отложенной записью ссылок в рамках согласованного шага. Для вложенных старых сущностей без нового ID (цены, уровни, рёбра зависимостей) журнал хранит целевого владельца и устойчивый ключ элемента; не выдаёт новый Guid за реально отсутствующий ID value object.

Отдельно переписываются полиморфные ссылки, строки с ID, BBCode/ссылки в документах и deep links, распознаваемые audit-ссылки и ключи задач. Для непонятных `EntityType`, `ReferenceType` и форматов содержимого выводится диагностика без значений полей. Не выполнять глобальную текстовую замену похожих на ULID подстрок.

Предлагаемая последовательность импорта:

1. Зафиксировать экземпляр источника, commit и контрольный момент снимка; открыть согласованный источник только для чтения. Выделить карту ID. На этом этапе production-schema сверку заново не запрашивать (D-416).
2. Справочники и базовые владельцы: роли/клиентские источники/клиенты/сотрудники/услуги/цены/категории. Разрешить отсутствующие источники и длительности прежде, чем считать блок готовым.
3. Курсы, группировка, темы/документы/зависимости/уровни, затем назначения и прогресс. Сотрудники должны быть определены до назначения преподавателей.
4. Графики, отпуска и заявки с решениями; серии и все существующие встречи, включая удалённые/отменённые. Восстановить только доказанные связи.
5. Платежи/расходы и явно полученные из старого расчёта финансовые факты после разрешения M-04. Не вызывать команды новых результатов.
6. Credentials/сессии/клиентские и календарные ссылки, затем push с зависимостями. Порядок технических записей уточняется после выбора хранения; доступ остаётся закрытым до успешной сверки.
7. История задач, дедупликация, произвольные задачи, уведомления/доставки, объявления/получатели и аудит. Фоновые исполнители до конца сверки не запускаются.
8. Сверить данные и доступ, записать завершение шагов, подготовить новые Quartz jobs. Открыть работу одной версии после принятого переключения. Предметные побочные эффекты и исторические уведомления повторно не производятся.

Это порядок зависимостей, а не обещание одной гигантской транзакции. Runner фиксирует отдельные шаги; checkpoint и соответствия ID должны сохраняться атомарно с данными шага. Повтор после сбоя не создаёт вторые сущности и не пропускает незавершённые преобразования.

## M-01. Клиенты и контакты

Прямо сохраняются ФИО, дата рождения и известный источник. `ClientProfile.SourceId` nullable для восстановления исторического неизвестного источника; Create/UpdateProfile требуют его по D-113, а Restore допускает null. Фиктивный справочник не создаётся. `Client.CreatedAt` сохраняет исходное время; исходный `IsLeadClosed` преобразуется в единый `IsArchived` по D-537, без новых финансовых операций. Вычисляемый этап отношений не определяется первым платежом. Отдельного старого поля клиентских заметок в snapshot нет. Схема, импорт и ограничения — в [хранении клиентов](client-storage.md) и [результатах переноса](client-import.md).

`AddClientCreationDate` задавала старым строкам техническое минимальное время; его нельзя принимать за реальную дату появления клиента или переписывать текущим временем. Аналогично крайние/infinity значения моментов читаются явно, без переполнения при приведении к DateTimeOffset.

По одному непустому Phone/Email/Telegram/Vk создаются контакты соответствующего вида. Для Link нельзя автоматически получить http(s) URL из произвольного username/номера без правила вида контакта. Шифротекст сначала расшифровывается с исходной версией ключа; при ошибке строка не считается пустой/невалидным телефоном. Исходное представление и нормализованное значение разделяются по D-412. По одному контакту данного вида у клиента можно предложить сделать основным, но конкретный ввод/канонизация ещё не выбраны.

Связанные строки должны переноситься по владельцу, несвязанные — выдаваться отдельным перечнем для ручного разрешения. Наличие 62 таких строк в старой локальной фикстуре не означает то же количество на production. Пробел в учётной записи клиента не разрешает отдать его контакт другому клиенту.

По D-418 у клиента может быть ноль контактов. Если все его старые контактные поля пусты, переносится клиент с пустым списком без фиктивной контактной записи и без предупреждения только из-за отсутствия контактов. Для каждого непустого вида сохраняется один основной. Непустой нерасшифрованный/невалидный контакт не превращается в пустой, а несвязанная строка по-прежнему требует разбора.

## M-02. Идентичности и доступ

Старые значения `Roles.RoleName`: 1 Superuser → `StaffRole.Superuser`; 2 Admin → `Administrator`; 4 User → `Teacher`; 8 Client → клиентская идентичность через `Users.ClientId`. Новые значения enum — 0/1/2, поэтому числовой cast неверен. Нестандартная комбинация flags или клиентский User без ClientId требует разбора. Сотрудника, который ведёт занятия, нельзя определить только по названию роли: Superuser/Admin тоже могут быть провайдерами. `Staff.Participates` устанавливается по согласованному предметному основанию, а не автоматически по роли 4.

У `Staff.Name` нет раздельного хранения имени/фамилии, контактов или PasswordResetRequired. `StaffLogin.HasPassword` не заменяет парольный хэш. Старые сотрудники могут иметь маркер сброса пароля после Stage8; он не считается рабочим хэшем. В `CredentialHasher` референса используется формат `mt-argon2id-v1$` и внешние pepper; `AuthenticationTokenHasher` использует HMAC для refresh и SHA-256 для opaque token. Персональные данные защищает отдельный protector, `Users.EmailBlindIndex` вычисляется из email и ключа.

Техническая реализация должна сохранить необходимые версии ключей/pepper, совместимую проверку уже выданных credentials и признаки отзыва, либо иметь конкретную адресную процедуру перехода. Файлы ключей и реальные значения не входят в Git/артефакты инвентаризации. Передача всех пользователей через повторную регистрацию, повторное применение Stage8 или массовый сброс доступа этим документом не выбираются. Новый срок сессии нельзя получить как `now + 14 days` вместо сохранённого истечения; создание объекта не должно продлевать старый доступ.

В источнике нет passkey-таблиц. Новые приглашения, recovery и браузерный каталог аккаунтов требуют собственного хранения; старые Used/Revoked/Expired не должны стать действующими. Нужно отдельно спроектировать отсутствие старого времени создания сессии: не выдавать ULID timestamp или время импорта за доказанную дату создания.

## M-03. Услуги и встречи

| Старый Appointments.Status | Новый AppointmentStatus | Значение enum в rewrite |
| --- | --- | --- |
| 0 Planned | Scheduled | 0 |
| 1 Completed | Completed | 1 |
| 2 Cancelled | Cancelled | 3 |
| 3 Burned | Burned | 2 |

Статусы сопоставляются по смыслу. `IsDeleted` переносится независимо от статуса и не превращается в Cancelled. В источнике нет RoomId: историческая встреча получает допустимое `RoomId = null`, без выдуманного кабинета. `LessonNotes` нужно добавить в предметное/историческое хранение, не подменять им выбранную тему или текст ДЗ.

`EndDate - StartDate` даёт исходную длительность конкретного занятия, а не текущую длительность услуги. Неположительная, дробная по минутам или не входящая в 30/45/60/90/120 длительность требует предупреждения; округление запрещено. Услуга не имеет Duration. Исходный генератор серий задавал 60 минут, но это не доказывает такую длительность всех вручную созданных встреч. До реализации требуется явная политика длительности услуги: возможны выбор по подтверждённым однородным данным либо отдельная настройка при неоднородной истории. Исторические встречи сохраняют собственную длительность.

`ProviderId` старой встречи nullable, новый `StaffId` обязателен. Подставлять владельца сервиса, текущего администратора или «первого преподавателя» нельзя. У новой отменённой встречи есть CancellationReasons, а старый Status не содержит причины. Совпадение с отпуском не доказывает, что он вызвал отмену. Для таких случаев нужны ручное разрешение/явное представление неизвестной причины; не присваивать Manual и не создавать компенсации автоматически.

`Service.PublicNameOverride` сохраняет именно старый override с fallback на Name; одинаковые значения не доказывают отсутствие пользовательской настройки. Description нужно сохранить. Для IsPublic и прочих новых признаков выбирается явное начальное значение; наличие PublicName не является доказательством публикации.

## M-04. Деньги и историческая цена

Старый `ClientWithBalanceDtoMapper` считает сумму всех Payments клиента минус стоимость не удалённых Completed/Burned. `ClientBalanceCalculator` передаёт **StartDate** в `DashboardPriceResolver`: берётся последняя цена с EffectiveDate ≤ началу; если ранней цены нет, берётся самая ранняя вообще; если истории услуги нет — 0. При одинаковом EffectiveDate разные цены не имеют отдельного tie-break по ID. В `RecurringTaskCandidateService.ResolveDebtorAppointmentPrice` fallback иной: при отсутствии предыдущей цены получается 0. Это различие старых экранов/долговых задач нужно измерить отдельно, а не объявлять единой старой формулой.

Новый `Service.PriceAt` и `SettlementSelection` работают по окончанию занятия; баланс требует явных `AppointmentSettlement`. В старой БД таких фактов нет. Предложение: для импортируемых не удалённых результатов создать производный факт денежного списания с суммой старого расчёта по началу, с пометкой происхождения/алгоритма и исходной встречей. Это фиксация старой суммы, а не вызов новой команды SetResult и не создание дополнительного платежа. Для новых результатов применяется новый расчёт по окончанию. Формат хранения происхождения, отсутствующего RecordedAt и пограничные случаи нужно определить до реализации. Время импорта не выдаётся за время старой отметки результата.

Случаи смены цены внутри занятия, отсутствующей цены, одинаковых дат цен, удалённого Completed/Burned и отрицательных/слишком точных numeric проверяются отдельно. Нельзя округлить всё до двух знаков или создать нулевые списания при неоднозначности без диагностики. Текущая модель Money допускает два знака, источник numeric такого ограничения не имеет. Проверяются баланс каждого клиента, сохранённые платежи/расходы и объяснимое соответствие сумм, а не только общий итог школы.

`Payments.ServiceId` сохраняется как исходное назначение, даже если новый денежный баланс единый. Строка платежа с ServiceId не доказывает покупку абонемента, покрытие занятия или возврат. Старые Payments/Expenses.Date — timestamptz; Payment сохраняет момент, Expense.Date сейчас DateOnly. Нужно сохранить исходный момент расхода дополнительно, а московскую дату вычислять отдельно. Не создавать Refund по одному отрицательному Payment без разбора его смысла.

## M-05. Серии, UTC и исходная позиция

Источники: `RecurringAppointmentService`, `RecurringAppointmentMaterializer`, `AppointmentDeletionService`, `Api/Schedule/AppointmentUpdatePreparationService` и тестовые сценарии этих границ в референсе. Старый генератор использует сохранённые UTC Date/TimeOfDay, без поля timezone. Weekly — битовая маска Monday=1 … Sunday=64, Monthly — номер дня с **пропуском месяца**, если такого дня нет; это не новое правило календарных задач с сокращением месяца. Встречи генератора имеют 60 минут.

При переводе Weekly в Moscow переводятся **пары день+время**, а не только часы: позднее UTC-время может перейти на следующий местный день. StartDate/EndDate правила и крайний включительный день тоже разбираются с семантикой старого генератора. Копирование маски прямо в enum Weekday неверно. Daily/Monthly не поддержаны новой Series — это ожидаемые расхождения схемы, а не свидетельство наличия таких строк на production. При их наличии требуется ручное решение (D-399), без потери будущего расписания.

Старые встречи не имеют исходного ordinal/времени до индивидуального переноса; материализация устраняет дубли по `(RecurringRuleId, StartDate)` и учитывает существующие удалённые/отменённые строки. Пропущенные из-за отпусков кандидаты могут вовсе не иметь строки. Удаление/разделение серии могло изменить правило или отвязать старые встречи. В источнике нет сохранённого курсора материализации.

Алгоритм восстановления предлагается строить так:

1. Для каждого сохранённого правила перечислить теоретические кандидаты старым алгоритмом в согласованном диапазоне и сопоставить фактические встречи, включая удалённые. Зафиксировать случаи повторяющегося старта и отсутствующих ссылок.
2. Точное совпадение по правилу и времени — основание для кандидата, но **не доказательство отсутствия прежнего переноса**. Проверить доступный аудит/изменения правила; при неоднозначности не назначать ordinal по сортировке фактических встреч.
3. Если исходная позиция доказана, назначить SequenceNumber по исходному порядку кандидатов и перепривязать эту позицию к фактической встрече; индивидуальные отличия персонала/времени сохраняются как overrides только при доказанном основании. Compensates не выводить из соседних отменённых встреч.
4. Пробел в строках не означает SeriesSkip: это может быть отпуск, не просмотренный диапазон материализации или изменённое правило. Не создавать пропуски/конфликты для всей отсутствующей истории автоматически.
5. NextDate/NextSequenceNumber вычислять после классификации прошлого и существующих будущих встреч. Нельзя просто взять `max(StartDate) + week`: так можно потерять более ранние ещё не материализованные будущие кандидаты. Дальний горизонт новой бессрочной серии — отдельная операция после восстановления и сверки.

Полный доказуемый алгоритм для неоднозначных переносов пока не реализован. Неоднозначные правила получают предупреждение для ручного разрешения; импорт не запускает материализацию, компенсации и задачи конфликта как побочный эффект. Отвязанные встречи не прикрепляются к похожему правилу по одному совпадению клиента и даты.

## M-06. Отпуска и рабочие графики

После Stage14 все три пары границ отпуска/заявки уже timestamptz и конец исключительный. Сохраняются исходные моменты, без повторного `+1 day`, без округления до московских суток. Старые таблицы отпусков разделены по субъекту, новые объединяются с discriminator; карты ID учитывают исходную таблицу.

VacationRequests.Status хранится строкой: Pending → Pending, Approved → Approved(mapped vacation), Declined → Rejected, Cancelled → Withdrawn. Approved без существующего ResultingVacationId соответствующего типа/субъекта — не успешное согласование, а предупреждение. RequesterPrincipalType/RequesterId, SubjectType/SubjectId и ProcessedBySuperuserId логические, не защищены FK. `ResultingVacationId` не означает целевой отпуск для новой заявки на изменение: такое основание отдельно не записано в старой модели.

В старом Vacation нет IsDeleted и прямого RequestId. Нельзя выводить историю удалений из отсутствующих строк или создавать новые заявки для каждого отпуска. Предлагается сохранять автора, времена подачи/решения, Version и исходный статус в явной истории заявок; текущей модели для этого не хватает полей. Право будущего одобрения остаётся BIZ-01 и не влияет на сохранение уже принятого решения.

UserWorkingHoursDays хранит недельные локальные минуты и IsWorkingDay; это текущий график, а не версия с EffectiveFrom. У Sunday значение 0, у нового Monday — 0. Для 1440 нельзя создать TimeOnly(24,0): это конец следующих суток; преобразование должно сохранить длину и границу. Полные сутки 0–1440 не представляются текущим LocalTimeWindow с одинаковым началом/концом и требуют отдельного разбора. Исключённые/нерабочие дни не превращаются в круглосуточную работу. Новый LocalTimeWindow допускает переход через полночь, но это не основание изменить старое окно.

Отсутствие всех строк графика у существующего пользователя имело определённый смысл: `UserAvailabilityService.GetDefaultWorkingHours` подставлял понедельник–пятницу 10:00–20:00, выходные — нерабочие. Это производный исходный факт, который нужно учесть при начальном графике; пустой новый график не обязан давать то же поведение. При частично заполненном наборе строк сервис не дополнял отсутствующие дни этим default. Историческую EffectiveFrom из default вывести нельзя.

WorkingHoursRequests и их дни — отдельная история предложений, а не снимки автоматически действовавших графиков. В источнике нет EffectiveFrom: CreatedAt/ProcessedAt не доказывают начало действия. Нужны явное сохранение заявки/решения и правило начального действующего графика, без выдуманных исторических перерывов. Будущее изменение графика действует сразу после подтверждения супером D-435 с предварительным разрешением конфликтов D-444. Это не доказывает исторический EffectiveFrom источника.

## M-07. Курсы, учебная история и документы

Старая структура `Course → Block → Branch → Theme` несёт порядок, названия и описания. Новый Course содержит плоские Topics и Levels. BIZ-21 определяет дальнейшую группировку, но не разрешает уничтожить старую. В старом `CourseProgressService` открытие зависит не только от ThemeDependencies: требуются предыдущая тема ветки и все темы более ранних блоков. Перенос только явных рёбер может преждевременно открыть материал. Вариант преобразования этих условий в явные зависимости требует отдельного описания и сверки; не добавляется молча.

| Старый CourseThemeProgressState | Кандидат нового TopicStatus | Что остаётся сохранить/решить |
| --- | --- | --- |
| 0 BlockedByDependency | NotStarted | Сам статус блокировки и основания старой программы |
| 1 AvailableToUnlock | NotStarted | Отличие от уже открытого материала |
| 2 Unlocked | нет точного | Подмена Learning добавит факт обучения; NotStarted может снова закрыть доступ |
| 3 InProgress | Learning | StartedAtUtc и остальные времена |
| 4 WaitingForHomework | AwaitingHomeworkReview | WaitingForHomeworkAtUtc и остальные времена |
| 5 Completed | Mastered | CompletedAtUtc и прежняя привязка к урокам |

UnlockedAtUtc/StartedAtUtc/WaitingForHomeworkAtUtc/CompletedAtUtc — отдельные исходные факты, их нельзя восстановить из одного нового статуса. Старое назначение не хранит преподавателей; брать преподавателя из любой встречи того же клиента без подтверждения нельзя. Полное прохождение можно предложить вывести из состояния всех тем, но источник не хранит факт отдельного завершения курса; время завершения не выдумывается. Встреча с CourseThemeId связывается с назначением по клиенту/курсу только при однозначной существующей связи; новое назначение не создаётся ради удовлетворения FK.

Старые LessonContent/HomeworkContent выводились компонентом `BbcodeContent.tsx`: b/i/u/s/quote/code/url/list/* и текст. Это не произвольный HTML и не готовый LearningDocument. Новые DocumentText поддерживают bold/italic/link, но не underline/strikethrough/code; нужен формат без потери или согласованное расширение документа. Неизвестные теги/небезопасные URL не удаляются молча и не исполняются. Оригинальный текст сохраняется до проверенного преобразования. Формат новой схемы документа должен быть версионирован (D-404).

HomeworkContent темы — шаблон ДЗ, не доказательство персонального назначения или выполнения. LessonNotes — заметки встречи, не документ темы. В источнике нет таблиц PersonalAssignment/PracticeAttempt, поэтому их история не синтезируется из текстов или completed темы. BIZ-22/BIZ-23 не решаются переносом автоматически.

## M-08. Задачи и дедупликация

По D-417 пользователь подтвердил использование и обязательность **всех существующих задач**, дополнительно — напоминания о ДЗ за три дня до занятия. В набор входят AppointmentReminder, BirthdayGreeting, TrialFollowUp, InactiveClientReminder, TeacherDailySchedule, DebtorReminder и CustomTask. Напоминание о ДЗ создаётся за 72 часа до начала; прежние D-162–D-163 о настраиваемом интервале, немедленном создании при поздней записи, пересчёте при переносе и отмене незавершённой задачи при отмене занятия сохраняются. Это рабочие сценарии до переключения, а не только сохранение их истории. Отсутствующие варианты моделей и генераторы нужно добавить; исключение старых видов из новой версии не выбрано. Исторические напоминания о ДЗ из старых executions не выдумываются: у новой функции нет прямого исходного типа.

Старые RecurringTaskRules — правила вычисляемых кандидатов; открытая задача обычно не имеет строки в RecurringTaskExecutions. Таблица executions хранит обработку: Completed=0, Cancelled=1, Delayed=2. В новом WorkItem это Completed=2, Cancelled=3, Postponed=1 соответственно: снова требуется явное соответствие, не cast. У CustomTasks состояние задаётся отметками CompletedAt/CancelledAt/DelayedUntil, а не этим enum.

Новые SystemTaskKind не покрывают все старые типы. Старый AppointmentReminder ближе к LessonReminder(Appointment), DebtorReminder — к Debt, TrialFollowUp означает контакт после консультации, а новый ConsultationReminder — не автоматически та же операция. BirthdayGreeting, InactiveClientReminder, TeacherDailySchedule не имеют прямого аналога в текущем Domain. Их настройки и обработку нельзя молча отбросить или заменить календарным правилом. OffsetMinutes/CooldownDays имеют разную семантику по типу, знак/назначение Lead нельзя брать простым cast в TimeSpan.

DeduplicationKey содержит исходные ID и значимые компоненты: appointment-reminder включает rule/appointment/start/offset; birthday — rule/client/year; trial-follow-up — rule/appointment; inactive-client — rule/client/period date; teacher-schedule — rule/teacher/date; debtor-reminder — rule/client/business date. CustomTask использует `custom-task:{id}`. Источник — `RecurringTaskCandidateService` и `RecurringTaskPresentationMapper` референса. Перегенерация этих ключей на новых ID без сохранённого соответствия способна заново выдать уже обработанную задачу.

Предложение: хранить типизированное основание и перевод старого ключа в новый устойчивый ключ вместе с журналом исполнения. Дата BusinessDate — местная бизнес-дата, не заменяется CreatedAtUtc.Date; при истёкшем DelayedUntil сохранённая история отсрочки не исчезает. DueAt и прежнее содержание восстанавливаются только по известному типу/связям; CreatedAt не подставляется вместо срока. Для вычисляемых открытых кандидатов требуется согласованный контрольный момент снимка и отдельный перенос актуальной очереди с учётом истории; не запускать старый query-путь на production, поскольку соседние операции могут материализовать расписание.

CustomTasks хранят внешний RecipientName/Phone/Telegram/Vk даже без ClientId. WorkItem.OneOff не содержит получателя. Нельзя молча создать клиентскую карточку или потерять данные доставки. Создание/выполнение/отмена/отсрочка и их авторы/времена должны получить место в хранении. Конфликт CompletedAt и CancelledAt либо отсутствующее требуемое основание — предупреждение. Завершённые задачи не превращаются в открытые из-за смены enum/ключа.

## M-09. Аудит и исторические ссылки

Старый ActorUserId nullable и без FK; системные записи могут вовсе не иметь автора. Новый Actor допускает только Staff/Client, поэтому подстановка действующего суперпользователя недостоверна. Нужен способ хранить исторического/системного автора, исходные Category/Action/EntityType/EntityId/Details и снимки отображения автора; SourceIpAddress и контакты защищаются правилами доступа и не выводятся в логи/диагностику.

AuditEntry.Changes и FinancialEffects не восстанавливаются из свободного текста без проверяемого разбора. При распознанном EntityType и ID добавляется связь через карту; неизвестный или уже удалённый объект не означает разрешение удалить аудит. Старый ID/текст сохраняется как исходный факт с ограниченным доступом, без фиктивной новой сущности для удовлетворения ссылки. Предлагаемое хранение исторического аудита должно поддержать чтение новой системой; исходная БД не считается его готовой реализацией.

## M-10. Календари, уведомления, объявления и push

CalendarSubscriptions старой версии имеют Token и один из UserId/ClientId; на уровне БД нет CHECK ровно одного. Проверены `RegenerateUserCalendarSubscriptionEndpoint`, `RegenerateClientCalendarSubscriptionEndpoint` и `GetCalendarSubscriptionEndpoint`: UserId выбирает календарь **провайдера**, ClientId — календарь клиента. Сотрудник с административной ролью мог выпустить ссылку для другого пользователя/клиента, но создатель отдельно не сохранялся. Поэтому субъект известен, а автор выпуска ссылки из этих полей не восстанавливается. В новой модели нужно определить Owner без выдуманного автора и ClientAccessId без выбора случайной клиентской ссылки.

Нужно проверить оба/ни одного владельца, клиентскую роль в старом UserId и все состояния отзыва. Календарь провайдера включал не только встречи, но и его открытые задачи; их нельзя молча потерять при переходе на CalendarEvent только для Appointment. Старый GET feed вызывает материализацию встреч, поэтому его нельзя использовать для read-only инвентаризации production. ICS UID строился как `{старый AppointmentId}@melodytrack` (для задач — из rule/key); смена ID без сохранения внешней идентичности может дать дубли событий у подписчика. Это входит в карту внешних ссылок D-414. Текущий документ не разрешает сброс или расширение области старых ссылок; оригинальные URL и новые маршруты требуют сохранения доступности и выбранных правил доступа.

Notification.Event требует типизированные параметры, а источник хранит Type/ReferenceType/ReferenceId/DeepLink и снимок текстов. ReferenceId — nullable bytea ULID, ReferenceType — строка. Уже в старых workflow есть уведомления по `vacation_request` и `working_hours_request`, для которых в новом NotificationEvent нет вариантов. Неизвестное событие или недостающие параметры не превращаются в AppointmentCreated. ReadAt/ExpiresAt и исторические тексты должны сохраниться. Повторная доставка всех исторических уведомлений не выполняется. Параметры группировки и правила будущих объявлений остаются BIZ-26/BIZ-27; старые Audience/Severity/ShowBeforeAuthentication/состояния чтения и скрытия всё равно входят в перенос.

PushSubscription привязана к старой Session и одному User/Client. Её Endpoint/Auth/P256Dh — защищённые данные; ключи подписки не становятся моделью DevicePushPreference. После разделения сессий необходимо сохранить привязку к устройству и активному аккаунту без доставки сообщения другой личности (D-408). Для Delivered delivery сохраняется завершение; для Pending/Failed нужны явная граница повторов и дедупликация при переключении. Отсутствующее хранилище доставки не разрешает считать Pending уже доставленным или повторно отправить всё.

## M-11. Служебные данные и новый запуск

`__EFMigrationsHistory` относится к источнику; новый runner пишет свои шаги в `schema_migrations`. Копирование старых MigrationId в новый журнал не создаёт целевую схему. RequestReplays не переносится прямо в активный namespace новых endpoint: старый fingerprint/response может не соответствовать новому контракту. Предложение политики: сохранить исходную служебную историю, а новые команды начать в новом namespace; влияние на повтор запросов через окно переключения нужно определить до реализации. Это предложение, не согласованное удаление истории.

Quartz предлагается инициализировать заново из job-конфигурации rewrite. Не копировать активные locks/fired triggers/scheduler heartbeat и сериализованные payload со старыми CLR-типами в работающий новый scheduler. Исходные предметные серии, правила задач и обработанные executions переносятся отдельно; технический пропуск запуска компенсируется идемпотентной обработкой актуального состояния, без повторных бизнес-эффектов. Политика пауз/пользовательских календарей и pending работ уточняется по реально используемой конфигурации. Старый scheduler и запись приложения останавливаются на финальном переключении.

## Чего нет в источнике

В 45 таблицах источника нет покупок абонементов/их продлений, Refund, явных AppointmentSettlement, скидок/кампаний, Rooms, SchoolClosure, PersonalAssignment и PracticeAttempt, публичных профилей/контента сайта. Это вывод о схеме, не об отсутствии материалов во внешних файлах или конфигурации. Такие новые сущности создаются новыми сценариями, а не вымышленными историческими покупками/попытками. Цены услуги и платежи не являются доказательством существования абонемента. Сведения из внешних конфигураций/сайта требуют отдельного перечня, без копирования секретов в Git.

## Проверяемые соответствия для будущего пробного переноса

Эти проверки спроектированы, но сейчас не запускались.

| Область | Проверяемое соответствие |
| --- | --- |
| Покрытие | Каждая исходная строка имеет перенос, явное сохранение с чтением новой системой либо отдельно согласованное исключение. Нет необъяснённых строк/полей; статус Пробел не считается успехом |
| ID/FK | Каждая ссылка разрешена в правильном типе; соответствия уникальны и стабильны при повторе/продолжении, вложенные записи проверены по владельцу/ключу |
| Клиенты | Число клиентов, ФИО, дата рождения, источник и исходные флаги сверяются; число контактов объясняется разбиением и владельцами, а не равенством числу ClientContacts |
| Расписание | По каждой старой встрече совпадают моменты начала/окончания, длительность, статус, удаление, провайдер, услуга, заметки и тема. Нет новой материализации во время импорта |
| Серии | Для восстановленной позиции доказана принадлежность; нет дублей/потерянных будущих дат, молчаливых skips, сброса курсора и придуманной компенсации |
| Деньги | По клиентам совпадают платежи и принятая историческая сумма долга; разница цены start/end объяснена. Нет повторных списаний/оплат и выдуманных покупок |
| Отпуска/графики | Субъекты, точные интервалы и решения сохранены; даты не сдвинуты повторно; нерабочие дни не стали рабочими; нет выдуманного EffectiveFrom |
| Учёба | Сохранились дерево/порядок, материалы, зависимости, прогресс и времена. Сравниваются доступные темы и XP, а не только количества строк |
| Доступ | Рабочие/отозванные/истёкшие состояния и область доступа сверены; ни одна учётная запись не получает новые права по ошибке числового enum. Токены/контакты не выводятся |
| Задачи | Обработанные ключи не рождают повторную задачу; сохранены отсрочки, закрытия, получатели и история авторов; вычисляемая очередь сверена на один момент |
| Коммуникации/аудит | Сохранены получатели, ссылки, чтение/скрытие, тексты и история; исторические Delivered не отправляются повторно; системные авторы не выдуманы |
| Повтор/сбой | Сбой откатывает данные шага с checkpoint и картой ID; повтор не создаёт дубли. Пустая БД и путь импорта приходят к одной целевой схеме |

## Порядок следующей реализации

Сначала можно проектировать схему прямых справочников, цен, платежей и базовых владельцев с учётом nullable/исторических полей. Однако текущие C#-записи нельзя механически объявить полной целевой схемой: M-01–M-11 перечисляют реальные пробелы.

До схем соответствующих блоков нужно определить хранение недостающих исходных фактов, credentials/сессий и истории, способ фиксации старой стоимости, а также разбор неоднозначных серий. Одобряющие BIZ-01, направление стадий BIZ-15 и применение графика BIZ-20 выбраны. Курсы/ДЗ отложены D-446, а состав счётчика BIZ-39 и объявления BIZ-27 остаются открытыми; они не мешают инвентаризации других блоков. Решения DEV-03/DEV-04 не переоткрываются. После этого — миграции целевой схемы и импорт по зависимостям с проверками на изолированной копии PostgreSQL 17.
