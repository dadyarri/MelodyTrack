## Роли и короткие маршруты

Координатор выбирает минимально достаточную работу. На каждый вызов передаёт исходную задачу, источники/ID, границы diff, разрешённые пути, явный статус разрешения проверок и ожидаемый результат. Агент возвращает факты с источниками, решения/предложения отдельно, проверки и блокеры. Лимит параллельности наследуется от среды; модели и глобальные функции не меняем.

| Специализация | Вызов | Изменения и передача |
|---|---|---|
| requirements_analyst | новое правило, legacy, влияние | только назначенный проект требований/запись; вопросы пользователю, затем critic |
| domain_critic | существенное изменение требований | только чтение; контрпример, правила, последствия; конфликт обратно аналитику/пользователю |
| software_architect | границы, контракты, транзакции | назначенная техническая документация; значимый выбор пользователю |
| backend_developer | утверждённая реализация | назначенные src/tests/docs; неоднозначность аналитику, данные migration specialist |
| frontend_developer | назначенный UI/контракт | назначенные UI/тесты в существующем `web/` по его AGENTS; другое приложение только по явной задаче |
| qa_engineer | независимые сценарии и проверка | назначенные тесты/план, без исправлений продукта; пробел аналитику, дефект разработчику |
| code_reviewer | законченный diff | только чтение; реальные findings с последствиями/воспроизведением |
| data_migration_specialist | схема/преобразование/импорт | по умолчанию ревью; назначенные новые шаги/тесты; запуск реальных операций отдельно |

Read-only ограничения ролей — инструкции, не отдельная sandbox: все агенты наследуют полномочия родителя. Дополнительные Security/UX/DevOps/API/Documentation роли не нужны: относящуюся проверку получает reviewer, frontend или architect. Специальный security skill выбирается по его поддерживаемым языкам и условиям, не автоматически по слову «безопасность».

### Пересечения ответственности

Вход каждой роли указан в её TOML; общий формат поручения и ответа — ниже. Для всех восьми ролей действуют одинаковые правила владения состоянием и наследования настроек из раздела совместимости.

| Роль | Возможное пересечение | Как разделить работу |
| --- | --- | --- |
| requirements_analyst | архитектор и специалист миграций могут затронуть те же требования | аналитик готовит назначенный проект требований; остальные возвращают замечания, утверждение остаётся пользователю |
| domain_critic | analyst/reviewer проверяют те же инварианты | критик читает исходные правила, не редактирует их; координатор выбирает конкретную независимую границу проверки |
| software_architect | developer/migration specialist могут менять технические документы | назначить одного владельца документа; архитектор не меняет код приложения |
| backend_developer | QA и migration specialist могут затронуть тесты и схему; frontend — контракт | разделить тестовые файлы и новые шаги миграций; согласовать request/state/result/error до изменения потребителей |
| frontend_developer | backend/generator могут менять generated API, QA — UI-тесты | назначить владельца генерации и тестов, соблюдать web/AGENTS; generated файлы не редактировать вручную |
| qa_engineer | разработчик может одновременно исправлять те же тесты | назначить файлы/сценарии; QA не исправляет продукт, передаёт воспроизведение разработчику |
| code_reviewer | разработчик может менять diff во время ревью | передать законченную пачку; reviewer только читает, координатор сообщает о последующих изменениях проверенных границ |
| data_migration_specialist | backend/architect могут менять миграции, SQL и план преобразований | по умолчанию ревью; явно назначить новые шаги/тесты/план, выпущенные шаги не менять; реальные операции требуют отдельного разрешения |

Совместное чтение допустимо; пересечение изменений требует решения координатора до редактирования. Передавай между ролями только выводы, необходимые следующей подзадаче, а не полную историю предыдущего агента.

- **Новое требование:** analyst → ответы пользователя → проект изменения → независимый critic → устранение существенных вопросов → подтверждение пользователя → architect при изменении границ → developer → QA и reviewer по риску. Проверки после законченной пачки и разрешения.
- **Изменение правила:** тот же путь плюс связанные ID/состояния/права, история и существующие данные, миграции, API/UI и тесты. Не переутверждай всё приложение.
- **Баг:** нормативное ожидание → воспроизведение/регрессионный сценарий → минимальное исправление → разрешённая проверка. Маленький баг ведёт основной агент; независимая роль нужна при конкретном риске, а не ритуально.
- **Рефакторинг:** без согласования бизнеса при сохранении поведения/контрактов; используй IDE refactoring skill для semantic rename/signature, когда доступен. Проверки требуют обычного разрешения.
- **Legacy:** analyst собирает свидетельства и классифицирует; перенос неизвестного правила зависит от ответа пользователя. Не запускать старую систему/импорт ради чтения истории.
- **Данные:** architect/migration specialist готовят mapping и восстановление; пользователь подтверждает неизвестную семантику и разрушительные действия; developer работает в согласованном объёме.

Независимому критику/QA/reviewer передавай сырые требования, diff и проверяемые артефакты; не подсказывай ожидаемое заключение или рассуждения автора. После исправления перечитываются изменённые границы, а не запускается бесконечное взаимное ревью. Без новых существенных замечаний заканчивай.

## Передача контекста и владение состоянием

Основной агент восстанавливает [снимок](development/current-task.md) по [процессу](development/README.md), сверяет его с Git и кодом, определяет цель и границы, выбирает роли, проверяет и интегрирует результаты. Он единственный редактирует общий снимок/индекс задач, разрешает противоречия и переносит устойчивые сведения в существующие источники. Не передавай полную историю чата или историю другого агента; достаточно относящихся фактов, ссылок и критериев. Постоянный документ меняет только явно назначенный владелец в пределах своей роли.

Поручение содержит только применимые поля:

```text
Цель: конкретный результат подзадачи.
Контекст: существенные факты, утверждённые ID/статусы, необходимые выдержки.
Границы: ответственность, владелец файлов, исключённые/параллельные области.
Источники: относящиеся документы, файлы и символы, границы diff.
Ограничения: инварианты, неоднозначности, разрешения на проверки/данные.
Завершение: проверяемые критерии результата.
Изменения: разрешённые пути и действия либо только чтение.
Результат: нужные выводы, артефакты и формат ответа.
```

Субагент читает применимые инструкции, изучает лишь необходимую область, проверяет существенные утверждения снимка по коду; не решает вопросы вне поручения. Архитектура служит навигацией, а спецификации и принятые решения — нормативным основанием. Исследователь возвращает пути/символы, факты, предположения, вопросы, расхождения и кандидатов на сохранение вместо пересказа файлов. Read-only роли не редактируют документы. Разработчик проверяет исходное состояние, соблюдает назначенные файлы и критерии, сообщает о неоднозначности и необходимых обновлениях публичного контракта/документов; проверки выполняет только в разрешённом объёме после готовой пачки. Reviewer независимо читает diff и связанный код, проверяет критерии, инварианты и актуальность документации, возвращает приоритетные findings с причинами, отделяя доказанные дефекты от рисков.

Ответ пропорционален подзадаче; неприменимые разделы можно опустить:

```text
Статус: завершено / частично завершено / заблокировано.
Результат: выводы с источниками или выполненная работа.
Изменения: файлы и существенные изменения, если применимо.
Проверки: фактические команды/область/результаты и пропуски.
Ограничения и открытые вопросы: блокеры, неоднозначности, риски.
Контекст для сохранения: только новые устойчивые сведения или незавершённость.
Следующее действие: конкретное продолжение, если нужно.
```

Не запускай агента ради тривиального действия, не дублируй одно исследование несколькими ролями без конкретной причины. Параллельно выполняй только независимые подзадачи; назначай владельцев файлов, согласовывай пересечения до изменений, не отменяй чужой diff. Общий снимок остаётся у координатора; отдельный временный handoff допустим только для длительной подзадачи по [правилам снимков](development/README.md#снимки-и-контрольные-точки). На контрольных точках координатор сохраняет проверенные результаты; субагенты не ведут конкурирующие версии общего состояния.

### Существующая конфигурация и границы совместимости

Все восемь `.codex/agents/*.toml` содержат только `name`, `description`, `developer_instructions`: собственные model/reasoning/sandbox/tool overrides отсутствуют. Настройки наследуются из среды; read-only — ограничение инструкции, не отдельная sandbox. Персонального каталога `$CODEX_HOME/agents/` при исследовании не обнаружено, именованных глобальных ролей в `config.toml` нет. Проверены только необходимые поля, конфигурация и авторизация не менялись.

Локальный CLI — `0.166.0`; в просмотренной пользовательской конфигурации основной model — `gpt-6.1-sol`/`medium`, defaults субагентов — `gpt-6-luna`/`high`. Это наблюдение окружения, не проектное требование и не гарантия модели конкретного вызова: фактическая сессия может задавать свои параметры. Использовать существующее разделение стоимости там, где оно применимо; сложные неоднозначности/интеграцию оставлять координатору или профильному architect. Не менять модели, effort или лимиты ради этого процесса.

Изменены только строки `developer_instructions`, без новых TOML-параметров. Формат сопоставлен с [официальной документацией](https://learn.chatgpt.com/docs/agent-configuration/subagents) и проверяется существующим структурным валидатором. Доступность ролей в текущей сессии подтверждена перечнем инструмента делегирования; применение новых строк новой IDE-сессией требует проверки именно в том клиенте. Отдельная платная сессия ради проверки не запускается. Встроенные explorer/worker/default не имеют проектных TOML; при использовании получают этот контракт в поручении.

## Детерминированные проверки

Утилита `scripts/agent_checks.py` — тонкая Python 3.11+ stdlib обёртка, не test runner. Настоящие проверки выполняют dotnet/xUnit, npm/Vitest и Playwright. Перед `run`/`rerun-failed` с dotnet требуется elevated shell: возможен restore. При отказе не пробовать альтернативы. Команда `plan` ничего не запускает. Не передавай credentials параметрами команд. Артефакты игнорируются Git; полные логи локальны и не предназначены для публикации — перед передачей проверяй содержимое. Используй синтетические данные: обёртка не гарантирует удаление секретов из произвольного вывода стороннего процесса.

Текущие проверки: Domain/Application и Api unit tests без Docker; Init интеграционные тесты с PostgreSQL Testcontainers. Live import не входит в обычный набор. Scope `frontend` запускает неизменный `npm run verify:fix` в `web/` после готовой пачки и разрешения: Biome с записью изменений, TypeScript, Vitest и Vite build. Мутации форматтера нужно просматривать. Scope `browser` запускает `npm run test:browser`: Chromium, desktop WebKit и mobile WebKit всегда в Docker, включая прямой npm-запуск и rerun-failed. Требования и сборка образа описаны в [web/README.md](../web/README.md). Хостовые браузеры не используются; Vite работает внутри контейнера без публикации порта на хост. `--browser-project chromium` ограничивает проекты (флаг можно повторять); сводка явно называет ограничение. `--browser-port 5189` меняет внутренний порт вместо 5174. При наличии fnm используется `fnm exec --using 26 npm`, иначе npm из PATH. При отмене runner даёт процессам 15 секунд на очистку контейнера, затем завершает принудительно. `--scope all` сохраняет прежний backend-only смысл.

HTTP business outcomes в browser suite синтетические; cookie-запросы проходят через настоящий локальный HTTP-сервер. IndexedDB, cookies, BroadcastChannel, Web Locks и DOM настоящие. Регистрация и вход с виртуальным ключом проверяются в Chromium через native WebAuthn/CDP, а в desktop/mobile WebKit — через перехват API Playwright `context.credentials.install()`; аппаратная Safari-приёмка этим не покрывается. Native wheel проверяется desktop Chromium/WebKit; mobile WebKit вместо пропуска проверяет незаблокированные синтетические touch-события, CSS-изоляцию прокрутки, программную прокрутку настоящего списка и нативный tap по последнему пункту. Это не нативный свайп; точные границы — в [web/README.md](../web/README.md). Через обёртку JSON, traces и error contexts сохраняются в уникальный каталог запуска `.artifacts/agent-checks/`; прямой npm browser-запуск сохраняет прежний `web/.artifacts/browser/`. Unit-тест генератора проверяет порядок команд и include-path через fake dotnet, не регенерирует клиент. Полный API acceptance с реальным браузером и сервером, coverage и actual mutation testing в эти команды не входят.

```bash
python3 scripts/agent_checks.py plan --scope domain
python3 scripts/agent_checks.py run --scope domain
python3 scripts/agent_checks.py run --scope all
python3 scripts/agent_checks.py plan --scope frontend
python3 scripts/agent_checks.py run --scope frontend
python3 scripts/agent_checks.py plan --scope browser --browser-project chromium --browser-port 5189
python3 scripts/agent_checks.py run --scope browser --browser-project chromium --browser-port 5189
python3 scripts/agent_checks.py summary
python3 scripts/agent_checks.py details --help
python3 scripts/agent_checks.py rerun-failed --run <run-id>
```

Точный CLI и форматы описаны в `python3 scripts/agent_checks.py --help`. `all` означает build и обычные тестовые проекты rewrite, не продуктовую приёмку, live import или старый монорепозиторий. Проверка данных в реальном источнике — отдельная задача. Сборка в scopes `all` и `build` сохраняет `build.binlog` в каталоге запуска для диагностики MSBuild.

Каждый запуск сохраняет уникальный каталог `.artifacts/agent-checks/`: JSON с версией схемы/командами/status/exit codes/временем/итогами/ошибками и ссылками на артефакты, краткую сводку, полные логи и нативный xUnit XML либо Vitest/Playwright JSON. Успешный запуск требует успешного процесса и полных ненулевых результатов тестов; пропуски названы отдельно. Повреждённый/нулевой отчёт — incomplete; ненулевой неизвестный код — ошибка инструмента с сохранённой неопределённостью, не автоматически дефект приложения. `details --index N` раскрывает одну ошибку; сводка не печатает assertion values и stack traces. Падение Biome/TypeScript/Vite может не дать тестовый JSON: сохраняются статус, exit code и полный лог pipeline.

`rerun-failed --run <run-id>` повторяет backend-методы, отдельные Vitest-тесты или Playwright-тесты по исходному отчёту. Vitest запускается через `npm run test` с точным файлом и экранированным полным именем; форматирование, typecheck и build не повторяются. Playwright получает список точных сочетаний проекта, файла и пути названий describe/test, сохраняя исходный порт; flaky также повторяется. Новый отчёт ссылается на родительский и отмечает `subset_passed`, не успех полного набора; исходный отчёт не меняется. Фактически выполненные тесты сверяются с выборкой. Старые отчёты без полного списка идентичностей, неоднозначные имена, неподдерживаемые символы фильтра и ошибки pipeline без упавших тестов требуют повторения scope. Повтор не подтверждает устранение остальных ошибок исходного pipeline.

Выбран встроенный native xUnit XML: для него не нужны дополнительные пакеты. У xUnit есть также собственный TRX export; Microsoft TRX extension в проектах отдельно не задан. Поддержка: [xUnit MTP](https://xunit.net/docs/getting-started/v3/microsoft-testing-platform), [XML v2](https://xunit.net/docs/format-xml-v2). Для компилятора краткая выборка текстовых diagnostics — явно ограниченный fallback, оригинальный вывод сохраняется; regex не определяет успех. Дедупликация не должна склеивать разные test ID/location. Сводка ограничивает вывод и указывает способ открыть остальные ошибки.

Повтор провалившихся методов включает все theory cases метода. Успешный повтор сохраняет связь с исходным запуском и статус subset; только новый исходный scope доказывает полный набор. При краше без XML раскрывай полный лог, а не объявляй отсутствие ошибок успехом.

Проверка самой инфраструктуры после готовой пачки:

```bash
python3 scripts/check_agent_infrastructure.py
python3 -m unittest discover -s scripts/tests -v
```

Новая продуктовая правка после проверки требует соответствующего повторения; не расширяй проверку без причины. Итоговый отчёт содержит выполненное/не выполненное, причины и точный scope, а не обещание «всё проверено».

## Использование в Codex

- «Используй $rewrite-requirements: проверь изменение правила … по текущим D-*; код не менять».
- «Реализуй согласованный сценарий … через $rewrite-delivery одной законченной порцией; проверки пока не запускай».
- «Попроси domain_critic независимо проверить раздел …; передай исходный запрос и правила».
- «Пачка готова: $rewrite-verification, проверь domain и покажи сводку».
- «Передай data_migration_specialist ревью mapping … без подключения к данным».

Формат: `.agents/skills/<name>/SKILL.md` с name/description и `.codex/agents/*.toml` с name/description/developer_instructions. Отдельный project config не нужен: автообнаружение не требует регистрации ролей. Ни sandbox, ни модель, ни глобальные MCP не переопределяются. Источники: [официальная документация skills](https://learn.chatgpt.com/docs/build-skills) и [субагентов](https://learn.chatgpt.com/docs/agent-configuration/subagents); проверенная локальная версия и границы доказательства указаны в разделе совместимости выше. Для обновлённых файлов используй новую сессию, если текущий клиент не обновляет обнаружение. Структурная проверка не доказывает регистрацию в каждом IDE-клиенте; при недоступности custom agent передай его инструкции обычному субагенту без дополнительного LLM-оркестратора.
