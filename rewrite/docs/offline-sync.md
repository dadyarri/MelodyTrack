# Офлайн-синхронизация: технический проект

Статус: предложение для ручного ревью. Это не утверждение нового бизнес-правила и не готовый wire-контракт. Нормативная цель — полная работа доступных функций офлайн и явное разрешение конфликтов; D-449 и D-499/D-502/D-528. Реализация очереди, повторы, конфликтные состояния и макет редактора остаются открытыми в [архитектуре](../../specification/architecture.md#офлайн-параллельная-работа-и-права--d-449).

## Исходное состояние

- `POST/PUT` карточки уже принимают `commandId`; создание, обновление/контакты и запись `client_card_commands` выполняются одной транзакцией. Повтор того же ключа с тем же автором, клиентом, операцией и защищённым отпечатком возвращает прежний результат; повтор ключа с другим содержимым отклоняется. Это реализовано в `ClientCardsStore` и `0016_CreateClientCardCommands.sql`.
- Карточка при изменении использует полное `expectedState` и сравнение текущих значений, а не номер версии. При расхождении операция получает конфликт без возврата чужого содержимого.
- Для заметок `PUT` принимает `commandId` и `expectedState`; история с ID команды и изменение `protected_notes` записываются атомарно. Повтор распознаётся по записи истории. Контракты описаны в [карточках](client-directory.md).
- В SQL нет общей ревизии карточки и журнала доставки событий. Текущая схема уже предоставляет устойчивые ключи отдельных команд, но не очередь офлайн-доставки, журнал результативных конфликтов или durable cursor.
- Кроме отдельного прогресса обучения по `staffId`, frontend хранит зашифрованный черновик и команду создания нового клиента (начальная порция ниже). Принадлежность локальных данных аккаунту и проверка версии при чтении обязательны по `web/AGENTS.md`; общий офлайн-клиент не реализован.

## Предлагаемая граница протокола

Офлайн-очередь хранит операции пользователя, а не снимок, который можно целиком перезаписать при синхронизации. Предлагаемый объём общего протокола — создание/изменение клиентской карточки и заметок, просмотр ранее загруженных списка и карточки, а также актуальные на момент последнего успешного чтения справочники источников и видов контактов. Архивирование не входит: оно заблокировано D-541 до подключения проверок зависимостей. Реализованный начальный объём указан отдельно ниже.

### Следующая порция: кэш серверных данных

Локальное чтение ранее полученных серверных данных необходимо для офлайн-работы D-449; первая реализованная порция его ещё не подключает. Следующий технический объём — записывать успешные ответы каталога клиентов, открытых карточек и справочников в существующее зашифрованное хранилище аккаунта. Это управляемый приложением кэш; секреты и ответы аутентификации в него не входят. Правила срока хранения и закрепления исходных данных — D-544.

Предлагаемое поведение: онлайн читать сервер и обновлять локальный снимок; при отсутствии связи читать ранее сохранённый снимок с явным временем получения и отметкой локального источника. Ошибка авторизации не превращается в разрешение показать кэш; обнаруженный отзыв обрабатывается по D-528. Ошибка записи кэша не скрывает успешный ответ сервера, но не выдаётся за сохранение на устройстве. Неизвестная версия не перезаписывается автоматически.

Страницы списка сохраняются вместе с нормализованными параметрами фильтра, сортировки и пагинации. Отсутствующий локальный запрос не считается пустым серверным результатом; загруженная страница не означает наличие всего каталога и не позволяет заявить о полноте произвольного офлайн-поиска. Карточки сохраняются по ID. Серверный снимок хранится отдельно от локальной ожидающей команды, чтобы фоновое обновление не стирало ввод и исходное состояние для проверки конфликта. При восстановлении связи снимки обновляются с сервера; текущий SSE остаётся механизмом инвалидации.

Критерии следующей порции: чтение сохранённых данных после перезагрузки при доступном приложении; изоляция аккаунтов и блокировка при выходе; понятное отсутствие загруженной страницы/карточки; сохранность ожидающей команды после обновления снимка; отказ IndexedDB не маскируется под успех локальной записи. Полный запуск приложения без сети дополнительно требует service worker и восстановления локального контекста доступа; сам кэш ответов этой возможности не обеспечивает.

Каждая команда в IndexedDB имеет версионированную оболочку:

```text
schemaVersion, commandId, ownerStaffId, aggregateType, aggregateId,
operation, createdAt, baseState, intendedChange, localStatus, attemptCount
```

`commandId` — постоянный UUIDv7, созданный до локальной записи и повторно используемый при каждой доставке. `baseState` — серверное состояние, на котором основано редактирование; `intendedChange` хранит пользовательский результат отдельно. Команда сначала атомарно записывается в локальную базу, затем применяется к локальному представлению с отметкой «ожидает синхронизации». Повторная отправка не генерирует новый ключ. Пакеты и их поля проверяются по `schemaVersion` до использования; неизвестная версия не интерпретируется и не перезаписывается.

При создании карточки клиент заранее генерирует `clientId` и `commandId`, как уже допускает действующий API; отдельное соответствие временного ID серверному не требуется. Зависимые изменения карточки/заметок не отправляются до подтверждения создания. Потеря ответа создания требует повтора исходного `commandId` с тем же `clientId` и содержимым, а не нового создания карточки.

Очередь индексируется по `ownerStaffId`, но сервер заново получает автора из текущей аутентифицированной сессии и не доверяет полю клиента. До и после смены аккаунта UI закрывает доступ к предыдущему локальному namespace. Пароли, одноразовые коды, токены и WebAuthn challenge не сохраняются в Web Storage или IndexedDB согласно `web/AGENTS.md`. Для текущей сессии refresh обслуживается HttpOnly cookie `mt.staff.refresh`, управляемой браузером; access token хранится в памяти frontend (контракт [аутентификации](authentication-api.md)). Сроки хранения и шифрование локальных персональных данных определены D-544–D-545; разделение по ID аккаунта само по себе не считается защитой локальной базы.

### Офлайн-личность, перезапуск и выход

При успешном входе локальная база связывается с `staffId` и версией схемы. После перезапуска без сети приложение может восстановить локальную офлайн-личность и показать ранее загруженные карточки и очередь, если пользователь не выполнял обычный выход; сохранённая роль не даёт права на новые серверные операции. Это технически обеспечивает D-497: автономный доступ сохраняется до ближайшей синхронизации, где сервер повторно проверяет сессию и права. Не хранить для восстановления личности пароль, challenge или bearer-токен; действующую refresh-cookie продолжает хранить браузер.

Обычный «Выйти» закрывает доступ к локальным карточкам и несинхронизированным изменениям во всех вкладках, но сохраняет их для повторного входа того же сотрудника согласно [D-543](../../specification/authentication.md#локальные-данные-при-выходе--d-543). Технически вкладки получают сигнал через `BroadcastChannel`, устанавливают сохраняемую отметку блокировки, очищают память и останавливают запросы/SSE; каждая вкладка также повторно проверяет блокировку при возврате в фокус. Перезапуск приложения не снимает её: снять блокировку может только успешный вход того же `staffId`; до этого локальный namespace недоступен. Отметка блокировки дополняет шифрование D-545, но не защищает от скомпрометированного runtime. «Забыть аккаунт» остаётся отдельным действием D-282.

## Доставка и атомарность на сервере

Клиент отправляет команды в исходном порядке для одного агрегата; отдельные агрегаты могут синхронизироваться независимо. После конфликта следующие команды этого агрегата остаются заблокированными до явного разрешения предыдущей: их база зависит от состояния, которое сервер не принял. После `applied` сервер возвращает неизменный результат команды на момент её commit. Только следующая команда, чья база действительно зависит от локального результата предыдущей, может быть перепривязана к этому результату с сохранением своего пользовательского намерения. Текущий GET нельзя подставлять вместо базы: он может включать чужие изменения, которых пользователь не видел. Независимая команда сохраняет исходную базу; последующее конкурентное изменение приводит к конфликту, а не к тихой перезаписи. После конфликта агрегатная очередь снова приостанавливается. Сервер обрабатывает каждую команду независимо, в транзакции:

1. Проверяет текущую личность и права, доступ к разделу и предметные ограничения на момент доставки (D-449/D-497/D-502). Авторизация не выводится из сохранённой локально роли или старых прав.
2. Проверяет `commandId`. Совпадающий ключ с тем же автором, агрегатом, видом операции и содержимым возвращает сохранённый результат; иной запрос с тем же ключом отклоняется. Защищённый отпечаток не содержит исходный текст команды и не попадает в журнал/диагностику.
3. Для первой порции сравнивает `baseState` с текущими полями: полное `expectedState` карточки и `expectedState.notes` заметки. Новая per-aggregate revision не вводится: действующий API уже защищает обе записи сравнением ожидаемого состояния, поэтому команда несёт ожидаемые значения, а не несуществующую ревизию. Ответ конфликта не обещает номер версии. При совпадении сервер валидирует команду, меняет предметные таблицы, пишет историю/аудит и атомарно сохраняет неизменный результат команды в receipt. Для заметок сохраняются отдельная история и текущее значение; для карточки — поля и контакты. Повтор команды возвращает этот receipt даже если объект с тех пор изменился; текущий GET остаётся отдельным чтением и не заменяет результат команды.
4. При несовпадении сохраняет/возвращает устойчивый статус конфликта для команды и только нейтральную причину и ссылку на объект. Актуальные поля клиент получает отдельным GET лишь после проверки действующего права чтения; если право отсутствует, закрытые данные не раскрываются. Команду автоматически не применяет.

Для синхронизации изменений сохраняется действующий SSE `GET /api/changes/events` с обезличенным `invalidate` по [контракту live-data](live-data.md); транспорт не заменяется. Для восстановления без пропусков предлагается durable outbox и pull по cursor. Выдача cursor должна иметь commit-order гарантию при конкурирующих транзакциях: простая sequence недостаточна, поскольку транзакция с меньшим номером может закоммититься после чтения большего cursor. Для первой реализации предлагается выдавать cursor через строку-счётчик, которую изменение блокирует и увеличивает в той же транзакции до commit; блокировка удерживается до commit, поэтому следующий cursor не становится видимым раньше предыдущего. Это сериализует фиксацию событий и ограничивает пропускную способность; позднее можно заменить механизм только с сохранением commit-order/no-gap инварианта. SSE остаётся сигналом для немедленного pull, а восстановление после разрыва читает события строго после последнего локально применённого cursor. Outbox содержит только event ID, cursor, тип агрегата и opaque ID; изменения данных перечитываются обычным авторизованным GET. Фильтрация прав выполняется и для pull, и для GET.

## Состояния очереди и разрешение конфликтов

Предлагаемые локальные состояния: `pending`, `sending`, `applied`, `conflict`, `rejected`, `needsReview`. Падение сети оставляет запись в `pending`; timeout возвращает её в очередь с тем же ID. Серверный результат хранится рядом с исходной командой до локального подтверждения, чтобы перезапуск вкладки не терял факт применения. Только подтверждение `applied` помечает команду выполненной; локальный оптимистический показ сам по себе не считается серверным сохранением.

Конфликт хранит неизменный исходный `baseState`, локальное намерение и статус сервера; закрытые серверные значения доступны только после успешной авторизации чтения. Редактор предлагает сравнить разрешённые текущему сотруднику значения и выбрать дальнейшее действие; система не делает merge по совпадению текста, времени или близости значений. Если пользователь формирует новую команду после ручного редактирования, это новый `commandId`, а старая команда сохраняется как разрешённая/отклонённая ссылка для восстановления и идемпотентности. Следующие команды того же агрегата не отправляются до завершения конфликта; после решения новая команда строится от последнего авторизованно прочитанного состояния.

Для «нет доступа» интерфейс предлагает предусмотренное D-499 ручное принятие/отклонение: отдельно показывает локальную операцию и полученное серверное состояние, когда его разрешено прочитать. Принятие подтверждает уполномоченный сотрудник с текущим доступом; сервер повторно проверяет исходную операцию по актуальным правилам авторизации и предметным проверкам D-502. Отказ прекращает её повторную доставку и сохраняет решение в локальной истории до очистки по утверждённой политике хранения. При отзыве доступа во время синхронизации соответствующие локальные данные удаляются при первой возможности D-528; уже зафиксированные серверные решения сохраняются. Устройство без связи не может узнать об отзыве немедленно, что соответствует D-528.

## Критерии предлагаемого общего протокола

Проверяемый сценарий: сотрудник с доступом загружает список, карточку и справочники; теряет сеть; перезапускает приложение; создаёт/редактирует карточку или заметку; сеть возвращается; команда доставляется ровно один раз; результат перечитывается с сервера. Затем второй сотрудник меняет тот же объект офлайн-сценария: первая команда не затирает серверное изменение и показывает конфликт. Тесты охватывают перезапуск вкладки, timeout после commit до ответа, повтор той же команды, повтор ID с отличающимся payload, смену аккаунта, отзыв доступа, неизвестную/будущую версию локальных данных, отказ IndexedDB и ошибки сети. В дополнение проверяется гонка двух транзакций выдачи cursor: pull после более позднего commit не теряет событие более ранней ещё не завершившейся транзакции.

Критерии технической приёмки: ни одна команда не подтверждается до устойчивой локальной записи; повтор доставки не дублирует бизнес-эффект; два разных ID не объединяются по сходству (D-401); сервер проверяет актуальные права и ограничения; конфликт требует явного выбора и не раскрывает данные без права чтения; данные и команды никогда не видны другому аккаунту; отзыв доступа удаляет затронутые локальные данные при восстановлении связи; отмена запросов и закрытие вкладки не повреждают локальную очередь; cursor не пропускает события после конкурирующих commits. Эти критерии проверяют механизм для карточек и заметок и не расширяют набор разрешённых офлайн-бизнес-операций.

## Сроки и защита локальных данных

Сроки и защита утверждены в [D-544–D-545](../../specification/authentication.md#срок-хранения-локальных-рабочих-данных--d-544). Секрет защищает случайный ключ аккаунта, а не используется напрямую для шифрования каждой карточки. Реализация использует Web Crypto: PBKDF2-HMAC-SHA256 с 600 000 итераций и случайной 128-битной солью; обёртка ключа и записи — AES-GCM-256 с новым случайным 96-битным IV. AAD связывает запись с аккаунтом, ID и версией. Данные вместе с типом записи, сроками и признаком сохранения исходных данных шифруются; подмена открытых метаданных не должна превращать неотправленную команду в удаляемый кэш. Параметры и версии проверяются перед криптографией. [Web Crypto](https://developer.mozilla.org/en-US/docs/Web/API/Web_Crypto_API), [AES-GCM](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/encrypt), [стоимость PBKDF2 по OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#pbkdf2).

Пароль передаётся для открытия только после завершения всех факторов и получения соответствующей серверной личности; во время незавершённого MFA находится только в памяти и очищается по отмене, ошибке, завершению либо истечению challenge. При passkey/cookie-восстановлении открытие запрашивается отдельно. Для аккаунта без пароля UI создаёт случайный 256-битный отдельный ключ и требует подтвердить сохранение вне приложения. Секрет не выводится в диагностику, URL или хранилище. Шифрование не защищает уже открытое приложение от кода того же origin, расширения или захвата памяти; очистка данных браузером может уничтожить неотправленные изменения.

Экстренный сброс пароля допускает уничтожение всей локальной работы по D-545. Автоматическая очистка по этому основанию пока не реализована: необходим достоверный серверный признак завершённого сброса, доступный устройству после восстановления связи, и его привязка к аккаунту. Несовпадение секрета при открытии vault не заменяет такой признак. Обычная смена пароля требует сохранения данных и переобёртки ключа при доступном прежнем секрете/ключе; это также отдельная интеграция, отсутствующая в первой порции.

Отметка выхода сохраняется в localStorage и независимо в IndexedDB; cookie-восстановление не снимает её. Успешный явный серверный вход снимает блокировку только своего аккаунта. BroadcastChannel, storage/focus/visibility-сигналы закрывают открытые вкладки; перед записью engine проверяет, что владелец и ключ ещё действительны. Если обе записи блокировки отказали, выход не выдаётся за завершённый. Отзыв доступа отдельно помечает обязательную очистку в IndexedDB: обычный вход её не отменяет, удалить отметку можно лишь атомарно с данными. После ошибки удаление повторяется при online/focus и до открытия аккаунта. Очистка по срокам работает при открытии, чтении просроченной записи и во время работы; CAS не удаляет конкурентно обновлённую или закреплённую запись. Удаление vault делает прежние экземпляры непригодными для записи. Окончательная очистка при «Забыть» остаётся открытым вопросом D-282, действие в обычное меню не добавляется.

## Реализованная первая порция

Подключены зашифрованное хранилище аккаунта, открытие при парольном входе и отдельная ручная разблокировка, межвкладочное закрытие и сохранение черновика **нового** клиента. Восстановленный черновик никогда не отправляется автоматически. Учебные формы и редактирование существующих карточек в это хранилище не записываются. При открытом хранилище новая попытка создания устойчиво сохраняет `commandId`, `clientId` и исходный ввод перед HTTP; при неподтверждённом результате повтор использует тот же пакет, редактирование приостанавливается. Подтверждение сохраняется до удаления локальной ожидающей команды. При явной ошибке валидации исходная отклонённая операция сохраняется отдельно, форму можно исправить. Для входа без пароля до создания отдельного ключа доступно прежнее серверное создание с явным предупреждением об отсутствии локального сохранения. При обнаружении потери прав на эту возможность её локальные данные удаляются (D-528).

Это начало реализации, не завершение D-449: отсутствуют service worker, запуск приложения без сети, локальный каталог/карточки/справочники, автоматическая очередь доставки, офлайн-редактирование существующих карточек/заметок и редактор конфликтов. Для общего протокола выше необходим серверный receipt: сейчас повтор create читает текущую карточку, update возвращает только предупреждение о дубликатах, notes — 204. Эти ответы достаточны для ручного повтора самостоятельного создания с неизменным ID, но не подменяют неизменный результат команды для цепочки зависимых изменений. Серверный receipt, outbox и pull-cursor остаются техническим предложением.

Предлагаемые статусы общего UI различают «На устройстве», «Ожидает отправки» и «Сохранено на сервере»; конфликт показывается отдельно, с действием по D-499. Это отражает локальную надёжную запись и серверное применение разными состояниями, не меняя утверждённой семантики. Следующая вертикальная порция использует карточный `expectedState` и ожидаемое поле заметок, сохраняет текущий SSE; outbox с commit-order cursor требует отдельной реализации и проверки.
