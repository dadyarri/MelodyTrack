# Фоновое обновление данных — D-478

Основание: D-478 в [реестре решений](../../specification/decisions.md) и поручение реализовать SSE с сохранением состояния интерфейса. Это описание технического контракта текущей реализации rewrite.

| Сценарий | Сервер | Интерфейс и проверка |
| --- | --- | --- |
| Успешное изменение через API | После успешного POST/PUT/PATCH/DELETE публикуется обезличенный `invalidate`; операции восстановления сессии не создают цикл обновлений | Текущие загрузчики перечитывают данные через Kiota; данные и элементы управления сохраняются во время фоновой загрузки |
| Первое подключение или восстановление | Поток сразу отправляет `invalidate` | Повторное чтение актуальных данных покрывает пропущенные события, включая перезапуск API |
| Временный обрыв или отсутствие heartbeat | Клиент закрывает зависшее соединение | Повтор подключения с ограниченной экспоненциальной задержкой, немедленная попытка при восстановлении связи; API по таймеру не опрашивается |
| Изменение доступа | Подключение требует действующую staff/client bearer-сессию; поток проверяет её актуальность | Перед инвалидацией серверных данных обновляется `/api/auth/me`; GET выполняются с актуальной авторизацией; недоступные клиентские данные убираются |
| Выход или смена аккаунта | Соединение отменяется | Незавершённые запросы и stream reader отменяются, поздние результаты старого аккаунта не применяются |

## Протокол

`GET /api/changes/events`, `Accept: text/event-stream`, bearer только в заголовке. Ответ не кешируется и отключает буферизацию у поддерживающих `X-Accel-Buffering` прокси. Долгоживущее соединение передаёт комментарии heartbeat и события:

```text
id: <непрозрачная последовательность>
event: invalidate
data: <непрозрачная последовательность>

```

События не передают сущности, идентификаторы пользователей, поисковый ввод или персональные данные. Данные получает только обычный авторизованный GET. `id` не используется как курсор журнала: повторное подключение всегда требует полной синхронизации активных загрузчиков. Медленный подписчик получает последнюю инвалидацию без накопления неограниченной очереди.

Клиент использует сгенерированный Kiota request builder и существующий middleware авторизации, отмены и безопасных ошибок. `ResponseHandlerOption` передаёт сырой `Response` парсеру SSE, чтобы не буферизовать бесконечный ответ. `EventSource` с токеном в URL не нужен. TanStack Query не добавлен: нынешние загрузчики обновляют своё состояние на общий сигнал без второй реализации запросов.

Сервер отправляет heartbeat каждые 30 секунд. Клиентский watchdog ждёт 45 секунд только в видимой вкладке с активным окном; в фоне он приостанавливается. Возвращение фокуса даёт существующему соединению новый полный срок ожидания, не пересоздавая поток. Если heartbeat так и не приходит, обычный reconnect восстанавливает соединение. Запросы `restore` и `me` при фокусе относятся к проверке сессии и сами по себе не перезапускают SSE. Истечение исходного пятиминутного bearer по D-089 по-прежнему закрывает поток; новое подключение использует актуальный токен.

## Границы

Уведомления принадлежат одному процессу API. Прямые SQL-изменения и изменения из другого экземпляра API не публикуют события. Масштабирование на несколько экземпляров потребует общего источника уведомлений. Перезапуск покрывается переподключением и чтением состояния. Журнал доставки, офлайн-запись и разрешение конфликтов не реализуются этой порцией.

Сейчас рабочий frontend сотрудника содержит каталог клиентов, releases и идентичность. Учебные данные остаются локальной демонстрацией и не заменяются серверными событиями. Поток доступен также действующей клиентской сессии; отдельного интерфейса клиентского кабинета в этой порции нет.
