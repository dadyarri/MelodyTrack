# Аудит автотестов: сессия, регистрация, passkeys и release history

## Объём и метод

Проверены production-компоненты и assertions для `entities/session`, регистрации по приглашению, staff sign-in, passkeys, shared API/contract и release history. Также выполнен read-only review Playwright harness. Ожидания оценены по нормативным источникам ниже; результаты централизованной проверки приведены в [общем аудите и сводке прогонов](test-quality-audit.md). Наличие assertion само по себе не считалось свидетельством успешного выполнения.

Из области исключены `employee-training`, `clients`, shared date/data-view. Browser harness использует реальную доставку auth cookie через локальный HTTP сервер, но синтетические auth/business outcomes; он не заменяет production API/DB интеграционные тесты. В `web/src/shared/lib/appearance.test.ts` и других несвязанных изменениях аудит не проводился.

## Read-only review browser harness

Просмотрены `web/e2e/browser.spec.ts`, `web/e2e/harness.tsx`, `web/e2e/cookie-server.ts`, `web/playwright.config.ts`, `web/vite.config.ts`, `web/src/shared/lib/passkeys.ts`, `web/src/pages/clients/ui/ClientsPage.tsx` и `web/package.json`. Браузерная часть использует настоящий Chromium/WebKit, IndexedDB, Web Locks и BroadcastChannel; это корректная граница проверки browser behavior, но не production API acceptance. `clientsRead` фикстура использует scope `available/any`, соответствующий production gate в `ClientsPage.tsx`. Остальные проверенные locator names соответствуют текущей разметке. Финальный browser run завершился 30 passed / 3 skipped / 0 failed; две причины пропусков native WebAuthn в WebKit и mobile wheel ниже.

- Virtual authenticator использует Chromium CDP и имеет явный skip для WebKit; пропуск ожидаемый, он не равен проверке passkey на WebKit.
- Сценарий WebAuthn gesture/cancel подменяет `navigator.credentials.create`, но проверяет `navigator.userActivation.isActive` в момент вызова; отдельный Chromium virtual authenticator тест создаёт credential без подмены.
- Auth route продолжает запрос на локальный ephemeral Node HTTP сервер в `web/e2e/cookie-server.ts`. Сервер выставляет `synthetic-session` с `HttpOnly`, `SameSite=Strict`, `Path=/api/auth`; браузер реально доставляет cookie серверу, который проверяет состояние сессии. Сервер возвращает synthetic auth outcomes и не проверяет production issuance/expiry/revocation. Остальные business API (`clients/options`, `clients` и другие) остаются synthetic route responses.
- В двух-tab тесте максимум конкурентных restore измеряется вокруг искусственной задержки ответа и проверяется равенством 1; это осмысленно проверяет Web Lock для данного сценария.
- Mobile интеграционный тест использует synthetic identity с `clientsRead` и synthetic `clients/options`/`clients`; он покрывает композицию экранов при заданном API контракте, а не реальные роли и данные.
- Два native virtual-authenticator сценария пропускаются в WebKit-проектах из-за Chromium CDP зависимости. Native wheel сценарий пропускается в mobile WebKit; он выполняется в desktop browser проектах. Остальные browser сценарии завершились успешно.

## Вывод и открытые ограничения

В охваченных production boundaries тесты содержат наблюдаемые проверки главных role/factor guards, отказов, отмены, конкурирующего refresh, устаревших ответов, cookie-backed restore, HTTP contract parsing и release acknowledgement. Ранее выявленные пробелы этой подзадачи закрыты новыми unit/UI assertions. Frontend unit и browser suites выполнены централизованно; точные итоги всех lanes и ссылки на отчёты находятся в [общем аудите](test-quality-audit.md). Это качественная оценка дизайна, не количественная оценка coverage и не утверждение полного deployment acceptance.

Остаются предметные ограничения: полный passkey sign-in через staff UI/API и cross-tab release-history `storage` event не имеют отдельного сценария; native virtual authenticator в WebKit и wheel boundary в mobile WebKit пропущены по возможностям окружения/проекта (соответствующий wheel сценарий выполнен в desktop). Synthetic auth server и synthetic business API не заменяют backend integration tests. Эти ограничения не отменяют успешный фактический прогон приведённых браузерных сценариев и не требовали менять product logic или выдумывать нормативное ожидание.
