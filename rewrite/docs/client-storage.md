# Клиенты, контакты и источники: первый блок хранения

Добавлены модели восстановления, SQL-миграции, [защита значений](personal-data-storage.md) и [первый пакет импорта](client-import.md): реализация M-01 [карты переноса](migration-map.md). Фокусные тесты успешно выполнены. Из выбранной локальной базы Aspire в отдельную PostgreSQL 17 перенесён весь клиентский блок; сверка значений и повторный запуск успешны. Результаты, локальная конфигурация и границы — в [описании импорта](client-import.md#результат-переноса-из-aspire). Прикладные запросы CRUD ещё отсутствуют; перенос остальных областей и приёмка production не выполнены.

## Модель и сохранение исходных фактов

Шаг `0014_UnifyClientWorkState.sql` объединяет существующие `is_lead_closed` и `is_archived` логическим ИЛИ, затем удаляет `is_lead_closed`. Выпущенные шаги не меняются. Обновление архивного признака использует уже установленный триггер постоянного отзыва клиентских ссылок/сессий. Возвраты, списания и изменения исходного расписания миграцией не выполняются.

`Client.CreatedAt` сохраняет исходный момент создания в UTC. Единственное сохраняемое состояние работы — `Client.IsArchived`; вычисляемый этап отношений отделён от него по D-537. Исходный `IsLeadClosed` импортируется в архив, отдельного текущего свойства модели для него нет. Новая фабрика `ClientRules.Create` принимает время от вызывающего кода; модель и Rules не читают системные часы.

`ClientProfile.SourceId` допускает null для представления старой неизвестной связи. `ClientRules.Create` и `UpdateProfile` требуют известный непустой источник по D-113. `ClientRules.Restore` допускает отсутствие источника, но проверяет непустой ID, если он задан. Таким образом, исторического клиента можно загрузить без выдуманного рекламного канала, а новая карточка не обходит обязательность источника. Чтобы отредактировать профиль старого клиента с неизвестным источником, потребуется указать источник.

`ClientRules.Restore` получает дату и архив явно, без исполнения новых финансовых операций или повторной классификации. Минимальная техническая дата из старой миграции сохраняется как минимальная, не заменяется текущим временем и не выдаётся за доказанную дату регистрации. Импорт сохраняет PostgreSQL infinity явным SQL-приведением.

`ClientContactRules.Restore` восстанавливает контакт существующего, в том числе архивированного вида. Он сохраняет исходные значение и комментарий, включая пробелы. Формат проверяется по текущему виду; непредставимые значения возвращают предметную ошибку для последующей диагностики по D-399. Это не путь молчаливого ремонта телефонов/ссылок. Создание нового контакта архивированного вида по-прежнему запрещено.

По D-418 клиент может не иметь контактов вообще: пустой список допустим при создании, восстановлении, замене списка и удалении последнего контакта. Проверяются уникальность ID и ровно один основной контакт каждого вида, который представлен в непустом списке. Нулевые/невалидные ссылки возвращаются на ручной разбор; отсутствие контактов таким нарушением не является. Особого фиктивного клиента, источника или контакта не создаётся.

## Целевая схема

| Таблица | Поля и назначение |
| --- | --- |
| `client_sources` | UUID, название источника без автоматического объединения одинаковых названий |
| `contact_kinds` | UUID, название, format типа PostgreSQL `contact_format` (`phone`, `email`, `link`), архив |
| `clients` | UUID, раздельные имя/фамилия/отчество, дата рождения `birthdate` (`ClientProfile.Birthdate`), nullable source_id, protected_notes, исходная created_at, единый is_archived |
| `client_contacts` | UUID, владелец-клиент, вид, protected_value, protected_comment, признак основного |

По D-419 фиксированные перечисления новой схемы используют нативные PostgreSQL enum. В первом блоке создан `public.contact_format`, отображённый на `ContactFormat` через `NpgsqlDataSourceBuilder.MapDomainEnums()` с явным snake_case-переводом меток. Справочник пользовательских видов остаётся таблицей `contact_kinds`. Дата рождения переименована из Birthday/birthday в Birthdate/birthdate; поле старого источника DateOfBirth не меняется.

API регистрирует уже настроенный NpgsqlDataSource. Для Init остаётся обычное соединение: миграция сначала создаёт enum, а отображаемый источник данных открывается после неё. Такое требование к порядку загрузки типов описано в [Npgsql](https://www.npgsql.org/doc/types/enums_and_composites.html).

`DatabaseQuery.WithParameter("format", ContactFormat.Phone)` создаёт типизированный Npgsql-параметр через `ICustomQueryParameter`: Dapper не получает возможность подставить числовой DbType. Глобальные TypeHandler/TypeMap Dapper не изменяются. Явный DbType для отображаемого enum и неизвестное значение C# enum отклоняются до подключения. Чтение возвращает ContactFormat или nullable ContactFormat, обычные и транзакционные запросы используют одну привязку. Добавлены сценарии чтения/записи всех трёх меток, NULL и ошибочных значений. Перед фиксацией этой порции пользователь сообщил о прогоне тестов.

Чувствительные значения выделены как `protected_*`: их записывает импортёр после защиты. Реализованы `PersonalDataProtector`, контексты `ClientDataProtection` и отдельный `LegacyPersonalDataReader`; формат и конфигурация описаны в [защите данных](personal-data-storage.md). Прикладных запросов CRUD ещё нет, открытые контакты/заметки в эти поля писать нельзя. В миграции нет настоящих значений, ключей или строк подключения. Нормализованное значение/индекс сравнения также ещё не добавлены: точный алгоритм D-412 не определён этой порцией.

Нет ограничения уникальности контактного значения между клиентами. Одинаковые названия источников/видов тоже не объединяются. Идентификаторы выдаёт приложение; в БД нет генерации ID или подстановки текущего времени, которые поменяли бы историю при повторном импорте. UUIDv7 и устойчивое соответствие исходным ULID по D-414 реализованы в служебных таблицах первого пакета импорта.

Физические поля имеют тип text без выдуманных новых лимитов, которые могли бы обрезать исходные данные. PK не допускают пустой UUID; связи защищены FK. Удаление используемого источника/вида запрещается; при разрешённом прикладном удалении всей клиентской карточки её собственные контакты удаляются вместе с ней. Проверки полномочий и других зависимостей остаются в Application и будущих FK соответствующих блоков.

## Контакты и транзакции

Клиент и изменения его контактов записываются в одной транзакции; отдельная карточка без контактов также допустима. Частичный уникальный индекс запрещает два основных контакта одного вида у одного клиента. Отложенный constraint trigger проверяет в конце транзакции ровно одного основного у каждого имеющегося вида. Для пустого списка проверять основной контакт не требуется; trigger обязательного наличия контактов удалён по D-418.

При смене основного сначала снимается флаг с прежнего, затем ставится новому: частичный уникальный индекс проверяется немедленно, а временное отсутствие основного допустимо до commit. При удалении последнего контакта одного вида группа исчезает и основной для неё больше не требуется. Можно удалить все контакты, сохранив саму карточку.

Перед изменением контакта trigger обновляет строку владельца, сохраняя is_archived без изменения. Эта адресная запись сериализует изменения контактов и создаёт версию строки для защиты от write skew при Repeatable Read; дополнительного обязательного счётчика версии клиента нет. При переносе контакта между владельцами обе строки берутся в порядке UUID. Будущие команды, меняющие несколько карточек, также должны соблюдать единый порядок; 40001/40P01 означают откат всей операции, а не разрешение сохранить её частично.

Причины отказа имеют стабильные имена: `ck_client_contacts_primary_required`, `ux_client_contacts_primary`. Сообщения trigger не включают ID, контакты или имена людей. Преобразование SQLSTATE/имён ограничений в API-ошибки ещё не реализовано.

Механизм отложенных constraint triggers описан в [документации PostgreSQL 17](https://www.postgresql.org/docs/17/sql-createtrigger.html); поведение строковых блокировок — в [Explicit Locking](https://www.postgresql.org/docs/17/explicit-locking.html).

## Отдельная база и граница готовности

`MigrationRunner.PrepareAsync` отклоняет базу с `public.__EFMigrationsHistory` **до создания** нового `schema_migrations`. Это защита от случайного направления нового Init в старую установку в выбранном сценарии отдельной целевой БД. Исходный журнал не копируется в активную историю нового runner. Источник во время будущего импорта открывается отдельно и только для чтения.

Тестовая фикстура Init переведена с PostgreSQL 16 на официальный образ PostgreSQL 17 с зафиксированным digest. Добавлены сценарии восстановления, исходных метаданных, создания без контактов и удаления последнего, отсутствующего/двойного основного у непустого вида, замены основного, одинаковых значений у разных клиентов, write skew под Repeatable Read и отказа от старой БД до записи истории. Конкурентный сценарий проверяет появление вида без основного после удаления прежних контактов, а не запрет пустой карточки. Тесты используют настоящую SQL-миграцию через копирование исходного файла в output, а не её тестовый дубликат. Перед фиксацией этой порции пользователь сообщил о прогоне тестов.

Реализованы read-only чтение источника, соответствия ID, импорт источников/клиентов/контактов, разделение общей строки контактов по владельцам и пообъектная сверка с повторным запуском. Следующий шаг — предоставить исходные ключи для повторной проверки OldDatabase и разрешить выявленные предупреждения. Подробные результаты и границы — в [отчёте первого пакета](client-import.md). Создание пустой целевой схемы и защита отдельных значений сами по себе не считаются переносом.
