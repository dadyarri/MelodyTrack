# Аудит backend автотестов rewrite

## Область и метод

Составлен inventory всех 97 C# test-классов и их публичных сценариев в трёх backend-проектах: Domain/Application (60), Api (13), Init/Persistence (24). По каждому тематическому блоку сопоставлены видимые сценарии с production-границами и нормативными источниками; подробно вручную разобраны высокорисковые Domain, auth, migration, client data, money, scheduling, task и permission areas. Не выполнялась построчная независимая проверка каждого assertion во всех 97 классах. Реальные мутации и измерение покрытия не выполнялись; этот документ не заявляет mutation score. Итоговую сборку и тесты запускал координатор после интеграции изменений; этот документ фиксирует результат ниже.

Общий аудит всех слоёв и сводный статус задачи приведены в [test-quality-audit.md](test-quality-audit.md). Успешный набор подтверждает состояние проверенного snapshot, но сам по себе не означает завершение параллельных product-code изменений.

Нормативная основа: `../specification/README.md`, `domain.md`, `appointments.md`, `scheduling.md`, `tasks.md`, `finances.md`, `access.md`, `authentication.md`, `clients.md`, `employee-training.md`, `migration-and-acceptance.md`, а также решения D-420–D-455, D-480–D-538 и относящиеся к конкретным разделам более ранние D-*. При неопределённом ожидаемом исходе ниже зафиксирован пробел доказательства или открытый вопрос, а не новый бизнес-контракт.

## Изменения тестов в этом аудите

- Каталог: `ClientDirectoryServiceTests` проверяет границу `q` 200/201 и отмену, пришедшую уже во время ожидаемого store I/O, включая передачу исходного токена. `ClientDirectoryEndpointsTests` проверяет тот же предел на HTTP-границе и отсутствие чтения store при отказе, no-store options и wire представление DateOnly/UTC instant. `ClientDirectoryStoreTests` проверяет 2/3 нормализованных цифры телефона, email/link поиск для разных владельцев, стабильные непересекающиеся страницы и пустые результаты, а также owner/ID/kind/name/format/value/comment/primary нескольких контактов.
- Миграции: `MigrationRunnerTests` теперь применяет реестр настоящих production migrations к пустой базе и проверяет вызов `levenshtein` после шага 0015, запись шага в истории и отсутствие оставшихся шагов.
- Cookies: `StaffSessionCookiesTests` дополнен IPv6 loopback. Общий `PostStaffAsync` в реальных auth endpoint tests теперь проверяет для каждого успешного staff POST-ответа: наличие cookie с тем же refresh token и атрибутами при выдаче токена либо отсутствие именно refresh-cookie для challenge-only ответа (endpoint filter может одновременно создать `mt.browser`). Это охватывает зарегистрированные вызовы password/passkey/factor/refresh/resume и challenge-flow через общий помощник. Restore flow проверяет ротацию cookie, отсутствие refresh-cookie для untrusted origin, истечение refresh-cookie при доверенном отказе сессии и повторный logout; успешный logout проверяет удаление cookie.
- Эти изменения — тестовые усиления; поведение production-кода не менялось.

## Сквозные качество и ограничения

- Domain suite преимущественно проверяет доменный результат/error variant и неизменность связанных финансовых/сессионных фактов; Init использует PostgreSQL и отдельную тестовую базу на сценарий. Это сильнее тестов, которые утверждают только HTTP 200.
- Отмена проверяется в DB query/transaction, store для каталога/обучения/import, API host и теперь mid-I/O Application каталога. Но полный каталог всех `CancellationToken` методов не сопоставлялся статически один-к-одному; остаточный риск — новый путь без передачи токена между слоями.
- Откат явно покрыт для migration runner, DB transactions, notes history и expense history; доменные appointment/payment tests утверждают отсутствие/реверсию финансового эффекта на отдельных отказах. Не каждый store сценарий имеет инъекцию отказа в каждую запись.
- Конкуренция покрывается целевыми race/replay тестами для расписаний/серий, permissions, notes, expenses, campaigns, employee training и auth sessions. Это выборочные контролируемые interleavings, а не exhaustive scheduler exploration.
- Тесты исторического импорта/миграций используют синтетические базы/фикстуры. Они не заменяют согласованную сверку с конкретной production-копией; никакие production data не использовались.
- Отдельный пробел требований не объявляется дефектом тестов с придуманным ожидаемым ответом. В частности, полнота cancellation для каждой фазы импорта, адресация редких DST значений и точные ошибки при внешнем transport outage требуют привязки к действующим правилам, прежде чем добавлять assertions.
- Для «transient restore» backend не задаёт отдельный временный HTTP-исход: server-side restore tests охватывают разрешённые/запрещённые/неавторизованные результаты; endpoint не имеет mockable transient service branch. При доверенном restore с невалидной/неактивной сессией API намеренно очищает refresh-cookie; на недоверенный Origin отвечает до чтения/очистки cookie. Повторный logout после отзыва проверяет отсутствие `Set-Cookie`. Восстановление после 429/503 — клиентский сценарий и покрывается frontend provider tests; backend fault-injection assertion потребует отдельного согласованного transient-контракта.
