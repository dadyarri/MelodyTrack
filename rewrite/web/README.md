# MelodyTrack rewrite — frontend

Отдельное React/TypeScript-приложение новой версии. Первая законченная порция: сотруднический вход по паролю или passkey, второй фактор, серверная идентичность, refresh и выход; адаптивная оболочка и первое обучение. Клиентские карточки и календарь подключаются следующими порциями.

## Запуск

Нужен Node.js 26. Из `rewrite/web`:

```sh
npm ci
npm run dev
```

Адрес — `http://localhost:5174`, порт фиксирован, чтобы не менять публичный origin passkey при каждом запуске. Для fnm без настроенного PATH:

```sh
~/.local/share/fnm/fnm exec --using 26 npm run dev
```

Запросы `/api` проксируются в rewrite API на `http://localhost:5280`. Другой адрес задаётся в `.env.local` через `MELODYTRACK_API_TARGET`; пример — `.env.example`. Это серверная настройка Vite, не секрет и не публичный API-ключ. В production остаётся принятый единый origin Kestrel; его интеграция с `web/dist` ещё не реализована.

Backend запускается отдельно из корня rewrite с его локальной секретной конфигурацией. Для passkey origin Vite нужно явно разрешить в конфигурации backend:

```text
Authentication__Passkeys__RelyingPartyId=localhost
Authentication__Passkeys__Origins__0=http://localhost:5174
```

Открывать приложение следует по `localhost`, соответствующему RP ID. Наличие двухшаговой кнопки passkey сохраняет пользовательский жест перед обращением к WebAuthn. Проверки origin/RP не отключаются. Создание первого сотрудника, приглашения и восстановление выполняются существующими серверными средствами; UI регистрации и восстановления в эту порцию не входит.

## UI и структура

Начальная библиотека — Ant Design 6. Общая тема задаётся в `src/app/App.tsx` через `ConfigProvider`, а собственные цвета и композиция — в `src/app/styles.css`. Основание настройки — [официальная документация Ant Design](https://ant.design/docs/react/customize-theme/). Существующие составные элементы (`Brand`, оболочка, страницы) принадлежат приложению; постепенная замена частей UI не требует менять API или предметную модель. Обёртка над каждым компонентом библиотеки не создаётся.

Импорты направлены вниз: `app → pages → widgets → features → entities → shared`. Соседние features не импортируют друг друга; их объединяет приложение. HTTP-контракт нового API проверяется в `shared/api`; старый Kiota-клиент не подключается. Текущая небольшая сессия управляется контекстом; общее хранилище серверных бизнес-данных пока не создаётся.

## Сессия и обучение

- Access/refresh tokens, пароль, коды и challenge находятся только в памяти. Перезагрузка требует нового входа; запомненные аккаунты и UI регистрации/восстановления будут отдельными порциями.
- Cookie браузерного контекста принадлежит backend, запросы передаются с `credentials: include`. Свойства роли и разрешений читаются из `/api/auth/me`.
- Изменения сессии между вкладками инвалидируют локальное состояние. Ошибка выхода не выдаётся за успешное завершение серверной сессии.
- Обучение автоматически появляется после первого входа сотрудника и допускает отсрочку. Учебная сессия полностью эмулируется без запросов к настоящему API.
- Персональный прогресс первоначального модуля хранится в IndexedDB на устройстве. Серверная синхронизация прогресса, доставка новых учебных версий, полная офлайн-работа и редактор конфликтов ещё не реализованы. Это начальная порция, не готовность всего механизма D-449/D-511–D-517.

## Проверки

После законченной пачки и разрешения пользователя:

```sh
npm run verify:fix
```

Команда применяет Biome, проверяет TypeScript, запускает Vitest и собирает production assets. Её изменения нужно просматривать. Проверки браузера выполняются отдельно; скриншоты и диагностические файлы находятся в игнорируемом `output/playwright/`.

Итоговый `verify:fix` первой порции завершился успешно: Biome, TypeScript, 18 тестов в четырёх файлах и production build. Сборка предупреждает о размере основного JS chunk: 689 КБ до gzip, 226 КБ после gzip; оптимизация загрузки остаётся дальнейшей работой.

В браузере проверены синтетические пароль/TOTP и ошибки HTTP/сети, запуск/отсрочка/прохождение/повтор обучения, локальное сохранение прогресса и компоновка на desktop/phone. Реальные аккаунты и данные школы для браузерных проверок не использовались. Аппаратная WebAuthn-приёмка не выполнена; успешный мок протокола не заменяет её.
