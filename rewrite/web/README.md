# MelodyTrack rewrite — frontend

Отдельное React/TypeScript-приложение новой версии: принятие приглашения сотрудника, настройка пароля/passkey и второго фактора, вход, серверная идентичность, refresh и выход; адаптивная оболочка, обучение, история релизов и каталог клиентов с просмотром карточки. Расписание подключается следующими порциями.

## Запуск

Нужен Node.js 26. Из `rewrite/web`:

```sh
npm ci
npm run dev
```

Адрес — `http://localhost:5174`, порт фиксирован, чтобы не менять публичный origin passkey при каждом запуске. Vite явно использует `localhost`; переходы на страницы через `127.0.0.1` или `[::1]` перенаправляются на `localhost` с сохранением пути и query. Это сохраняет соответствие RP ID ключей доступа и разрешённому origin восстановления сессии. Для fnm без настроенного PATH:

```sh
~/.local/share/fnm/fnm exec --using 26 npm run dev
```

Запросы `/api` проксируются в rewrite API на `http://localhost:5280`. Другой адрес задаётся в `.env.local` через `MELODYTRACK_API_TARGET`; пример — `.env.example`. Это серверная настройка Vite, не секрет и не публичный API-ключ. В production остаётся принятый единый origin Kestrel; его интеграция с `web/dist` ещё не реализована.

Backend запускается отдельно из корня rewrite командой `dotnet run --project src/MelodyTrack.Rewrite.Api`. Локальные подключения и ключи находятся в игнорируемом `src/MelodyTrack.Rewrite.Api/appsettings.Development.json`, который .NET загружает автоматически; `source` и экспорт переменных не нужны, в том числе в fish. Для passkey в этом файле настроены:

```text
Authentication:Passkeys:RelyingPartyId = localhost
Authentication:Passkeys:Origins = [http://localhost:5174, http://localhost:5280]
```

Открывать приложение следует по `localhost`, соответствующему RP ID. Под обычной формой логина/пароля расположена отдельная кнопка «Войти с ключом», которая сразу вызывает системный выбор ключа без проверки заполнения формы. Вкладок способов входа нет. Анонимный challenge готовится в фоне при открытии страницы и обновляется перед истечением срока, пока страница видима. WebAuthn не вызывается автоматически и не проходит через асинхронную валидацию формы. Проверки origin/RP не отключаются; для защищённых ролей после passkey по-прежнему требуется TOTP.

## Первый вход

Сначала запустите API и этот frontend. Затем из корня rewrite выполните одноразовую операторскую команду Init (синтаксис подходит fish):

```sh
dotnet run --project src/MelodyTrack.Rewrite.Init -- --Auth:Bootstrap true --Auth:SetupUrl http://localhost:5174/auth/register
```

Init выдаёт ссылку приглашения суперпользователя, действующую 24 часа. Откройте её и последовательно пройдите экраны: пароль → TOTP → passkey. Пароля по умолчанию нет. На каждом экране есть допустимый пропуск, учитывающий роль и уже настроенные средства входа. Если пароль пропущен, passkey обязателен; если суперпользователь/администратор пропустил TOTP, ему нужны пароль и passkey. Преподаватель с паролем может пропустить оба дополнительных этапа. В браузере без passkey сохраняется путь «пароль + TOTP». QR-код аутентификатора создаётся локально, ручной ключ также доступен. Код подтверждается до перехода к passkey, а не после создания ключа.

Приглашение передаётся в URL fragment, забирается до React и удаляется из адресной строки. Оно и промежуточные секреты остаются только в памяти. Перезагрузка страницы регистрации требует заново открыть исходную ссылку. Ошибка одноразового подтверждения требует начать настройку заново; при неоднозначном ответе сети можно перейти ко входу, если аккаунт успел создаться. После регистрации интерфейс проверяет `/api/auth/me` и открывает рабочую область либо запрошенный сервером дополнительный фактор.

Та же страница принимает приглашения других сотрудников и ссылки восстановления. Управление выдачей приглашений/восстановлением из кабинета и UI запомненных аккаунтов пока не реализованы.

## UI и структура

Начальная библиотека — Ant Design 6. Сохранена минималистичная бумажная палитра исходного приложения (`MelodyTrack.Web/src/app/styles/index.css` и `shared/config/theme/ThemeProvider.tsx`): тёплые поверхности, коричневый акцент и тёмная тема. Общая тема задаётся в `src/app/App.tsx` через `ConfigProvider`, а цвета и композиция — в `src/app/styles.css`. Основание настройки — [официальная документация Ant Design](https://ant.design/docs/react/customize-theme/). Составные элементы принадлежат приложению; обёртка над каждым компонентом библиотеки не создаётся. Рабочие экраны содержат короткие подписи; подробные инструкции доступны по запросу и в обучении.

Импорты направлены вниз: `app → pages → widgets → features → entities → shared`. Соседние features не импортируют друг друга; их объединяет приложение. Запросы выполняются сгенерированным Kiota-клиентом нового API. Сессия управляется контекстом. SSE `/api/changes/events` передаёт обезличенные сигналы обновления; каталог и история версий перечитываются в фоне с сохранением показанных данных и локального состояния интерфейса. Повторное подключение синхронизирует пропущенные изменения. Транспорт также использует Kiota с потоковым обработчиком ответа; [контракт и ограничения](../docs/live-data.md).

В верхней панели находится приветствие с серверным логином. По нажатию открываются переключение темы и выход. Обучение доступно из бокового меню; главная не содержит перечня глав, а статья не показывает отдельную метку прочтения. Учёт чтения для прогресса сохраняется.

Версия внизу бокового меню приходит из `/api/releases/current`; на телефоне она расположена под содержимым. Для суперпользователя и администратора нажатие открывает историю изменений с пагинацией. Новые изменения показываются автоматически после закрытия обучения; просмотр хранится отдельно для каждого аккаунта. Кодовое имя и его значение берутся с сервера, отсутствующая дата не отображается. Источник метаданных и механизм описаны в [`../changelog/README.md`](../changelog/README.md).

## Клиенты

Страница `/clients` использует компактную таблицу `DataView`: ФИО, статус, последняя/следующая запись, баланс, быстрые действия. Активный статус пустой, для архива есть метка. Недостающие занятия и баланс показаны прочерками, перенос выполняется отдельно. Нажатие на строку открывает правую панель с контактами, источником и датами. Фильтры — поиск, архив и источник; сортировка по нескольким полям задаётся стрелками заголовков. По умолчанию 10 строк, доступны 10/20/50/100; карточного режима и настроек вида нет. Доступ определяется эффективным `clientsRead`; область собственных клиентов ожидает связей расписания. Поисковый текст и карточки не сохраняются в браузере.

Кнопка «Помощь» и раздел «Обучение» открывают новый учебный модуль с самостоятельным упражнением. Подробности контракта, доступа и ограничения поиска: [список клиентов](../docs/client-directory.md).

## Генерация API-клиента

Из `web/` в elevated shell:

```sh
npm run api:generate
```

Команда восстанавливает закреплённый Kiota из `rewrite/dotnet-tools.json`, собирает всю rewrite solution и генерирует `src/shared/api/generated/` из build-time OpenAPI `src/MelodyTrack.Rewrite.Api/obj/openapi/MelodyTrack.Rewrite.Api.json`. Сервер экспортирует OpenAPI 3.0 штатным ASP.NET exporter без подключения к БД и без секретов; работающий API не нужен. В Development документ также доступен по `/openapi/v1.json`. Генератор и runtime закреплены отдельно от старого приложения.

В текущий клиент включены используемые маршруты регистрации и сотруднического входа, фактора, refresh, `/me` и выхода. При подключении новых возможностей список `--include-path` в `scripts/generate-api-client.mjs` расширяется. Сгенерированные файлы и lock-файл коммитятся; вручную и форматтером они не редактируются. Kiota 1.38.0 пока не включает `undefined` в optional property types, хотя его десериализаторы присваивают это значение. Завершающий шаг `web/scripts/normalize-kiota-optionals.ts` явно добавляет его в типы свойств; runtime-код не меняется. Шаг проверяется тестами, TypeScript проверяет весь клиент с сохранённым `exactOptionalPropertyTypes`. Описание подхода — [Kiota TypeScript](https://learn.microsoft.com/en-us/openapi/kiota/quickstarts/typescript).

`shared/api/http.ts` настраивает Kiota adapter: origin, bearer, browser cookie, отмену и безопасные ошибки. Маршруты, request builders и JSON-сериализация принадлежат generated client. Одноразовые запросы входа автоматически не повторяются. WebAuthn JSON передаётся через `additionalData` сгенерированной модели; состояние UI проверяется отдельно от необязательных полей HTTP-моделей.

## Сессия и обучение

- Access token, приглашение, пароль, коды и challenge находятся только в памяти. Постоянная HttpOnly-cookie refresh восстанавливает активную сессию после перезагрузки страницы и браузера; Web Storage и IndexedDB токенов не содержат. Истёкший или отозванный доступ требует полного входа. Переключатель нескольких запомненных аккаунтов остаётся отдельной порцией.
- Временные сетевые ошибки и HTTP 429/5xx обновления сессии сохраняют аккаунт и показывают ошибку. Повтор выполняется при возврате в приложение или восстановлении связи. Защищённое чтение ждёт уже запущенный refresh; после 401 допускается один обычный refresh и один повтор GET для того же аккаунта. Отзыв доступа и нарушение идентичности закрывают сессию. При старте восстановление не показывает промежуточную форму входа; временная ошибка допускает повтор. Cookie-запросы сериализуются между вкладками через Web Locks.
- Cookie браузерного контекста принадлежит backend, запросы передаются с `credentials: include`. Свойства роли и разрешений читаются из `/api/auth/me`.
- Изменения сессии между вкладками инвалидируют локальное состояние. Ошибка выхода не выдаётся за успешное завершение серверной сессии.
- Обучение автоматически появляется после первого входа сотрудника и допускает отсрочку. Учебная сессия полностью эмулируется без запросов к настоящему API.
- Кнопка запуска обучения сразу открывает демонстрационный аккаунт без ввода реквизитов. При первом автоматическом показе используется кнопка «Начать обучение». Пройденные упражнения сохраняют результат при повторе.
- Персональный прогресс первоначального модуля хранится в IndexedDB на устройстве. Серверная синхронизация прогресса, доставка новых учебных версий, полная офлайн-работа и редактор конфликтов ещё не реализованы. Это начальная порция, не готовность всего механизма D-449/D-511–D-517.

Запросы версии и истории также используют Kiota. Метаданные `/me` включают серверный `login` для приветствия; полная история доступна через `/api/releases`.

## Проверки

После законченной пачки и разрешения пользователя:

```sh
npm run verify:fix
npm run test:browser
```

Первая команда применяет Biome, проверяет TypeScript, запускает весь Vitest и собирает production assets. Изменения форматтера нужно просматривать. Второй набор требует браузеры Playwright (`npx playwright install chromium webkit`), их системные зависимости и свободный порт 5174. Он запускает Chromium, desktop WebKit и mobile WebKit; на Linux без совместимых системных библиотек используйте контейнер с ними и теми же версиями Node.js/Playwright.

Browser suite проверяет cookies/reload, две вкладки, Web Locks/BroadcastChannel, настоящий IndexedDB, фокус/viewport, композицию приложения и Vite redirect. HTTP business outcomes синтетические. Native WebAuthn через virtual authenticator доступен только в Chromium; сценарий явно пропускается на WebKit. Native wheel проверяется desktop Chromium/WebKit, mobile WebKit не предоставляет Playwright mouse wheel. Жест вызова chooser отдельно проверяется с синтетическим credentials API, включая WebKit без WebAuthn.

JSON, traces и error contexts лежат в игнорируемом `.artifacts/browser/`. Это не аппаратная WebAuthn/Safari-приёмка и не браузерный acceptance с настоящим API/PostgreSQL. Серверная интеграция запускается отдельно из rewrite через `python3 scripts/agent_checks.py plan --scope all` и разрешённый elevated `run --scope all`.

[Полный аудит тестов, фактические результаты и ограничения](../docs/test-quality-audit.md). Контракт каталога: [список клиентов](../docs/client-directory.md).
