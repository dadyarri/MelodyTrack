- Код и тесты доказывают фактическое поведение, а не его правильность. `docs/domain-models.md` фиксирует отставание моделей от D-420–D-455. Старые Backend/Web, roadmap и Git — исторические свидетельства; отсутствие правила в новой спецификации не подтверждает ни отмену, ни автоматический перенос.

## Реализация

- Domain — чистые сущности/Rules; Application — координация, авторизация и транзакционная граница; Persistence — SQL; Api — HTTP-отображение; Init — SQL/C# migration runner. Сначала прочитай относящиеся правила, затем реализацию.
- Сохраняй отмену до SQL/I/O, целостность и защиту персональных данных. Не выводи значения, секреты, connection strings или исходные персональные данные в отчёты/логи.
- Работай небольшими законченными порциями с ручным ревью по D-391. Не расширяй задачу на следующую порцию автоматически.
- Init использует собственные пронумерованные SQL/C# шаги: правила в `src/MelodyTrack.Rewrite.Init/Migrations/README.md`. Не используй EF-команды; выпущенные шаги неизменяемы. Запуск импорта, доступ к реальным данным и разрушительные операции требуют отдельного разрешения.
- Сохраняй родительские соглашения об именах/изоляции тестов, фокусных коммитах и запрете переписывания Git. Коммит, push и release не следуют из реализации задачи.

## Проверки и завершение

- Не запускай тесты, сборки, линтеры, форматтеры или verification pipeline между промежуточными правками. После законченной пачки изменений C# или MSBuild обязательно выполни итоговую сборку всей rewrite solution: `TreatWarningsAsErrors` включён, готовая пачка не должна оставлять предупреждений и ошибок сборки. Это постоянное разрешение на итоговую сборку и её повтор после исправления диагностик; elevated shell по-прежнему обязателен. Не подавляй диагностику и не ослабляй `TreatWarningsAsErrors` ради успешной сборки. Остальные проверки выполняй только по явному запросу либо после сообщения пользователя о готовности пачки к проверке. Поручение `analyze.md` явно включает итоговые проверки создаваемой инфраструктуры.
- Перед любой командой `dotnet`, способной обращаться к сети или implicit restore, запроси elevated shell, включая обёртки. При отказе/недоступности останови lane и сообщи блокер без обходных сетевых путей/подмены зависимостей.
- Общая точка проверок: `python3 scripts/agent_checks.py`; сначала `plan`, затем разрешённый `run`. Читай краткий отчёт и раскрывай `details` по необходимости. Подробности и ограничения — `docs/agent-workflow.md`.
- Для агентных файлов достаточно структурной проверки и тестов утилит. Для будущих frontend-изменений соблюдай локальные инструкции выбранного приложения; в старом Web разрешённая проверка — `npm run verify:fix` с просмотром мутаций.
- Готовность: согласованный объём выполнен; источники ожиданий, фактические проверки, артефакты, пропуски и нерешённые вопросы названы. Ненулевой exit code, ноль тестов, неполный отчёт и успешный subset не означают успех полного набора.

## Маршрутизация

- Повторяемые процессы: `$rewrite-requirements`, `$rewrite-delivery`, `$rewrite-architecture-data`, `$rewrite-test-design`, `$rewrite-verification`. Выбирай один вход по задаче, загружай остальные только при переходе границы.
- Специализации `.codex/agents/` вызывай выборочно по `docs/agent-workflow.md`. Эти инструкции разрешают делегирование для существенного анализа и независимой проверки; маленькую исправленную ошибку веди в основном агенте. Не запускай восемь ролей на каждую задачу и не строй рекурсивные цепочки.
- Родительские melodytrack-* skills с EF, старым Kiota, recurrence или Aspire относятся к старому приложению. Не переноси их пути/инварианты в rewrite. Общие skills переиспользуй по назначению; их процедуры не отменяют текущие требования и разрешения на проверки. Рекомендации обновления существующих компонентов — `docs/agent-infrastructure-audit.md`.


## Политика редактирования файлов

- По умолчанию используй `apply_patch` для изменения существующих текстовых файлов, включая Markdown, спецификации, конфигурацию и исходный код.
- Не используй временные Python-скрипты, Perl, sed и другие средства для простых текстовых замен, если ту же задачу можно выполнить через `apply_patch`.
- Для точечных изменений бизнес-правил и спецификации используй патчи с контекстом, позволяющим однозначно определить изменяемый участок.
- Не используй `str.replace()` с последующим `write_text()` для редактирования спецификации, особенно если совпадение исходного текста и количество замен не проверяются.
- Программные преобразования допускаются, когда задача действительно требует обработки большого объёма структурированных данных или сложных массовых изменений.
- При использовании скриптов проверяй предусловия, количество затронутых элементов и итоговый `git diff`.
- После изменения нескольких связанных документов проверяй согласованность внесённых изменений.
- Если `apply_patch` недоступен, используй наиболее безопасный доступный способ редактирования с явной проверкой результата.

## Актуальность и чистота спецификации

Спецификация описывает действующее состояние требований,
а не историю их обсуждения.

- В нормативных документах храни только актуальные
  утверждённые требования и необходимые пояснения.
- Не добавляй датированные комментарии вида
  «пользователь ранее сказал», «позже уточнил»,
  «в предыдущей версии предлагалось».
- При утверждении нового правила обновляй или заменяй
  прежнюю формулировку, а не дописывай историю изменений.
- Устаревшие и отменённые формулировки удаляй
  из нормативного текста.
- Не дублируй одно бизнес-правило в нескольких местах,
  если можно использовать ссылку на его источник.
- Неподтверждённые предложения храни отдельно
  от утверждённых требований.
- После разрешения открытого вопроса переноси
  только итоговое решение в спецификацию.
- Закрытые вопросы убирай из активного перечня.
- Не сохраняй хронологию промежуточных уточнений
  в нормативных документах.
- Для восстановления истории используй Git.
- Отдельные документы решений создавай только тогда,
  когда необходимо сохранить существенное обоснование,
  а не просто последовательность обсуждений.
- При неоднозначности действующего требования
  запрашивай уточнение, а не реконструируй его
  из исторических комментариев.
