Вход: согласованная задача, правила/сценарии, разрешённые пути. Прочитай `../../../AGENTS.md` и маршрут в `../../../docs/agent-workflow.md`.
1. Найди владельца поведения и потребителей: Domain → Application → Persistence/Api, тесты и данные. Зафиксируй небольшой законченный объём по D-391.
2. Для бага сначала установи воспроизведение и нормативное ожидание; для рефакторинга сохрани наблюдаемые контракты без нового согласования бизнеса.
3. Проверь влияние на состояния, права, HTTP/errors, транзакции, отмену, время и историю. Старые модели/тесты могут отставать от D-420–D-455.
4. При cross-layer работе согласуй таблицу request/state/result/error с backend и UI. Frontend rewrite отсутствует: не создавай его и не используй старый Kiota pipeline без задания.
5. Реализуй один путь, добавь тесты наблюдаемого поведения по риску. Не оставляй вторую постоянную реализацию. Не меняй пакеты/архитектуру ради удобства.
6. Заверши пачку; проверки только по разрешению пользователя, через $rewrite-verification. Передай QA/reviewer по риску исходную задачу, diff и артефакты, а не только своё заключение.
Стоп зависимой части: новое бизнес-решение, неясный контракт или неподтверждённое преобразование данных. Выход: изменения, привязка к требованиям, проверки/пропуски и ограничения. Готовность не равна готовности всего продукта или разрешению следующей пачки.
