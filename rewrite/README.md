# Новый бэкенд MelodyTrack

Изолированная реализация новой версии на C# 15 и .NET 11 RC2. Требования находятся в [спецификации](../specification/README.md). Работающая версия приложения не изменяется.

Серверный вход сотрудников и клиентов, факторы, восстановление, сессии и активный аккаунт браузера описаны в [контракте авторизации](docs/authentication-api.md). Там же приведены настройки passkey, серверный bootstrap и границы выполненных проверок. Frontend rewrite пока отсутствует.

Solution: [MelodyTrack.Rewrite.slnx](MelodyTrack.Rewrite.slnx). SDK зафиксирован в `global.json`: `11.0.100-rc.2.26504.105`, целевая платформа — `net11.0`. `Directory.Solution.targets` отделяет сборку от родительского шага генерации старого frontend. Источники NuGet наследуются из корневого `nuget.config`, версии управляются локальным CPM.

| Проект | Назначение |
| --- | --- |
| `src/MelodyTrack.Rewrite.Domain` | Чистые предметные модели, ограничения и расчёты |
| `src/MelodyTrack.Rewrite.Application` | Прикладные операции и порты; категории результата операции |
| `src/MelodyTrack.Rewrite.Persistence` | Npgsql/Dapper и реализации прикладных портов |
| `src/MelodyTrack.Rewrite.Api` | HTTP DTO, маршруты, host и преобразование результата в HTTP |
| `src/MelodyTrack.Rewrite.Init` | SQL/C#-миграции и инициализация БД |

Все проекты написаны на C#. Зависимости: `Application → Domain`, `Persistence → Application → Domain`, `Api → Application/Persistence`, `Init → Persistence`. В корневую `MelodyTrack.slnx` проекты не включены.

## Модели и идентификаторы

В Domain описаны клиенты и справочники, расписание и отсутствия, денежные операции и оплаченные резервы услуг, кампании и скидки, курсы и учебный прогресс, документы и практика, задачи и календарные правила, доступ и сессии, уведомления, аудит и публичные данные школы. Сущности содержат данные, предметные функции находятся в `Domain/Rules`, авторизация и координация — в `Application/Operations`. Команды с загрузкой/сохранением и хранение новых областей ещё не реализованы. [Карта покрытия спецификации](docs/domain-models.md) отмечает открытые правила. Подробности и открытые предметные решения — в [README домена](src/MelodyTrack.Rewrite.Domain/README.md).

Состояния с данными описаны иерархиями `closed record` с `sealed`-вариантами. Предметные объекты имеют закрытые конструкторы и неизменяемые свойства; переходы возвращают новое состояние. Коллекции представлены неизменяемыми массивами и множествами. Содержимое коллекций сравнивают явно: C# records не предоставляют структурное сравнение произвольных коллекций.

Идентификаторы объявлены в `Identifiers.cs` через StronglyTypedId Эндрю Лока:

```csharp
[StronglyTypedId]
public partial struct ClientId { }
```

Используется Guid-основа с JSON-конвертером и парсингом. Генератор подключён как приватная зависимость без runtime assets. Собственного генератора идентификаторов больше нет. StronglyTypedId допускает `default`/`Guid.Empty`; фабрики и изменения моделей отдельно отклоняют пустые идентификаторы с указанием поля.

## Результаты и ошибки

Модели используют `CSharpFunctionalExtensions.Result<T, ErrorList>`. `ErrorList` содержит непустой неизменяемый список `DomainIssue`: типизированную причину и необязательную предметную привязку к полю. Независимые проверки собирают ошибки вместе; зависимая операция прекращается при отказе предыдущей. Локализованные сообщения и пути HTTP DTO формируются в API. Необязательные значения представлены nullable-типами.

Application возвращает `Result<T, OperationError>` или `UnitResult<OperationError>`. Категории операции: валидация, конфликт состояния, отсутствие объекта и запрет доступа. Domain и Application не зависят от HTTP. Прикладные операции проверяют доступ и готовят изменения в памяти; команды с загрузкой и сохранением ещё предстоит реализовать; автоматическое преобразование любой доменной ошибки в одну HTTP-категорию не вводится.

`ApiResultExtensions.ToHttpResult` получает функцию успешного ответа и функцию отображения ошибки. Они определяют DTO, сообщения, внешние коды и пути полей. Успех может возвращать типизированный `Ok`, `Created` и другие ответы; `UnitResult` преобразуется в `204`. Ошибки становятся `ProblemDetails` со статусами 400/409/404/403 и массивом `errors` при наличии предметных причин. Сам `Result` в JSON не сериализуется. Для `traceId` endpoint передаёт канонический trace ID запроса.

## Доступ к БД

Публичный API Persistence содержит XML-документацию на русском языке с примерами DI-регистрации, параметризованных запросов и транзакций. В проекте включён `GenerateDocumentationFile`: при сборке создаётся XML-файл для документации потребителей сборки.

Используются Npgsql и Dapper. API регистрирует долгоживущий `NpgsqlDataSource` в DI из `ConnectionStrings:Database`, настраивает `NpgsqlDataSourceBuilder.MapDomainEnums()` и вызывает `services.AddDatabase()`. Обёртка `Database` получает источник через конструктор и регистрируется как singleton. Источником данных владеет host; отдельное соединение между запросами не разделяется. Пока строка подключения пуста, получить `Database` из DI нельзя; сама регистрация не открывает соединений. Типы PostgreSQL enum создаёт Init до первого подключения настроенного источника.

```csharp
var rows = await database.Query(sql)
    .WithParameter("clientId", clientId.Value)
    .WithParameter("archived", false)
    .GetAllAsync<ClientRow>(cancellationToken);

await database.Query(updateSql)
    .WithParameter("id", clientId.Value)
    .WithParameter("notes", notes)
    .ExecuteAsync(cancellationToken);
```

`Query(sql)` создаёт неизменяемый объект `DatabaseQuery`; каждый `WithParameter` возвращает новую ветку с собственным набором привязок. Повторное имя заменяет привязку только в этой ветке. Имена задаются без префикса или с `@`, необязательный аргумент `type` позволяет указать `DbType`, например для `null`. Значения передаются через `DynamicParameters`, без подстановки в SQL. На каждое выполнение создаётся отдельный набор Dapper-параметров.

Для отображаемого enum передавайте значение C# без явного DbType: `.WithParameter("format", ContactFormat.Phone)`. `DatabaseEnums` передаст его как типизированный Npgsql-параметр `public.contact_format`, сохранив метку вместо числа. Неподдерживаемое значение и явный DbType отклоняются до открытия соединения. Остальные типы параметров сохраняют стандартное поведение Dapper.

| Метод | Результат |
| --- | --- |
| `ExecuteAsync(token)` | `Task` без количества изменённых строк |
| `GetAllAsync<T>(token)` | Полностью прочитанный `IReadOnlyList<T>`, пустой при отсутствии строк |
| `GetSingleAsync<T>(token)` | Ровно одна строка; отсутствие и несколько строк вызывают исключение |
| `GetSingleOrDefaultAsync<T>(token)` | Строка или `default(T)` при отсутствии; несколько строк вызывают исключение |

Столбцы сопоставляются свойствам/конструктору модели стандартными средствами Dapper; имена при необходимости задаются через SQL aliases. Для простых значений можно использовать `GetSingleAsync<int>`, `GetSingleAsync<Guid>` и другие типы. В `GetSingleOrDefaultAsync<T>` отсутствие модели ссылочного типа означает `null`; для необязательного скалярного значения следует указать nullable-тип, например `int?`, чтобы отличать отсутствие строки от нуля. `ClientRow` обозначает проекцию SQL-строки; сложные доменные агрегаты создаются через свои фабрики, Guid преобразуется в типизированный ID на этой границе.

Обычный запрос автоматически открывает соединение из источника DI перед выполнением; отмена передаётся в открытие и `CommandDefinition`, результат читается до освобождения соединения. Исключения не подавляются.

Для нескольких запросов одной транзакции используется `Database.BeginTransactionAsync` и `await using`:

```csharp
await using (var transaction = await database.BeginTransactionAsync(cancellationToken))
{
    await transaction.Query(updateSql)
        .WithParameter("id", clientId.Value)
        .WithParameter("notes", notes)
        .ExecuteAsync(cancellationToken);

    var client = await transaction.Query(selectSql)
        .WithParameter("id", clientId.Value)
        .GetSingleAsync<ClientRow>(cancellationToken);

    await transaction.CommitAsync(cancellationToken);
}
```

`DatabaseTransaction` реализует `IAsyncDisposable` и владеет одним соединением и одной транзакцией. `transaction.Query(...)` использует тот же fluent-builder и передаёт транзакцию в Dapper. Все запросы такого scope, включая ветки `WithParameter`, выполняются на общем соединении последовательно. Независимые scope могут работать параллельно; `Database` не хранит текущую транзакцию в общем состоянии.

Commit выполняется только явным вызовом `CommitAsync(token)`. Можно явно вызвать `RollbackAsync(token)`; выход из scope без commit, в том числе через исключение, отмену или возврат ошибки `Result`, откатывает незавершённую транзакцию. Очистка не зависит от отменённого токена запроса. Соединение освобождается при `DisposeAsync`, даже если освобождение транзакции завершилось ошибкой. Повторное освобождение безопасно. После commit/rollback/dispose нельзя создавать или выполнять связанные запросы, включая созданные ранее builder-объекты.

`database.Query(...)` вне scope остаётся обычным запросом с отдельным соединением и не присоединяется к транзакции автоматически. `WithConnectionAsync` — внутренний механизм управления соединением; прикладной код использует публичные builder и транзакционные scope.

Init использует выделенное соединение без pooling для сессионной advisory-блокировки. Самописный runner и поддержка SQL/C#-миграций сохраняются. C#-обработчики компилируются вместе с Init, как прежние обработчики `.fs`; исполнения `.fsx`/`.csx` во время запуска не было и сейчас нет.

## Запуск и миграции

Ключевое требование к миграциям — перенос данных и истории предыдущей версии при свободе изменения схемы. Локальная `melodytrack` используется как неизменяемый источник: перенос проверяется только на отдельных копиях. Требования, начальная инвентаризация и сценарии проверки зафиксированы в [плане переноса](docs/data-migration.md).

Для принятого production-референса составлены [инвентаризация схемы](docs/source-schema.md) и [карта переноса](docs/migration-map.md). Они охватывают все 45 EF-таблиц, служебные таблицы, преобразования и пробелы текущих моделей. Первый клиентский блок успешно перенесён из выбранной локальной базы Aspire в отдельную PostgreSQL 17 со сверкой и повторным запуском; приёмка production этим не подтверждается.

`Api` пока запускает host без маршрутов на `http://localhost:5280`; старая версия сохраняет порт 5000. Реальные команды, HTTP DTO и контракты маршрутов будут добавлены вместе со сценариями. Добавлены [схема клиентов, контактов и источников](docs/client-storage.md) и первый пакет импорта; прикладная запись/чтение ещё не реализованы. Остальная предметная схема БД, авторизация, Quartz и frontend ещё не реализованы. SQL-запросы пишутся вручную и выполняются через Dapper.

`Init` исполняет сгенерированный при сборке реестр SQL/C# без поиска файлов, рефлексии и скриптов во время запуска. Он получает advisory lock на выделенном соединении, проверяет историю и применяет каждый шаг вместе с записью истории одной транзакцией. Обработчик получает подключение, транзакцию, отмену и логгер. Коды выхода: 0 — успех, 1 — ошибка, 2 — явный импорт требует ручного разбора, 130 — отмена. Подробности — [README миграций](src/MelodyTrack.Rewrite.Init/Migrations/README.md).

API и Init имеют собственные настройки и профили Development. Строка подключения `ConnectionStrings:Database` по умолчанию пуста; значение передаётся через `ConnectionStrings__Database`. `.env` и `appsettings.Local.json` автоматически не загружаются. Init читает конфигурацию относительно каталога приложения. В лог ошибок выводится тип исключения и, для ошибки миграции PostgreSQL, SQLSTATE и имя миграции; SQL, значения данных и подробности подключения не логируются.

Для старта API также требуются `PersonalData:CurrentKeyVersion` и `PersonalData:Keys:<version>` из секретной конфигурации: каждый новый ключ — 32 случайных байта в Base64. Эти настройки проверяются при старте; ключей по умолчанию нет. Добавлены защита клиентских полей и отдельное чтение старого шифрования для будущего импорта. Формат, смена ключей и текущие ограничения описаны в [защите данных](docs/personal-data-storage.md). Init для создания схемы эти ключи не требует.

Init поддерживает явный первый пакет импорта `--Import:Clients true`: источник `ConnectionStrings:OldDatabase` открывается read-only, цель остаётся отдельной `ConnectionStrings:Database`. Для этого режима нужны исходные `Import:LegacyKeys:<version>` и новые ключи `PersonalData`. Из Aspire перенесены 49 клиентов, 193 контакта и 6 источников. Подключения и ключи текущего переноса хранятся в игнорируемом `.env.import.local`, который нужно явно загрузить в окружение перед запуском Init/API; без него остаются прежние подключения из appsettings. Подробности, сверка и границы — в [описании импорта](docs/client-import.md#результат-переноса-из-aspire).

## Тесты и проверка

- `tests/MelodyTrack.Rewrite.Domain.Tests`: сценарии моделей, накопление ошибок, StronglyTypedId и защита от пустых идентификаторов; без Docker.
- `tests/MelodyTrack.Rewrite.Api.Tests`: преобразование результата, успешные ответы, статусы и JSON Problem Details; без Docker.
- `tests/MelodyTrack.Rewrite.Init.Tests`: генерация реестра, миграционный runner, жизненный цикл соединения, fluent-запросы и транзакционные scope Dapper на PostgreSQL/Testcontainers; один контейнер на тестовый класс и отдельная база на сценарий, нужен Docker. Проверки входа builder не используют БД.

Используются xUnit v3 и Microsoft.Testing.Platform v2. Сценарии прежних 166 доменных тестов перенесены на C#, проверки собственного генератора идентификаторов заменены проверками выбранной библиотеки и фабрик. 29.10.2026 пользователь подтвердил успешный прогон тестов после переноса, добавления fluent-запросов, DI-регистрации, транзакций и обновления проверок публичного API. Ассистент перед созданием коммитов повторно тесты не запускал.
