# Спецификация MelodyTrack v2

Статус: спецификация продукта ещё неполная. Технический каркас согласован D-382; после D-390/D-391 реализованы предметные модели/Rules, прикладные операции в памяти, инфраструктура SQL/Init и первый блок клиентов/импорта. Это не готовность всех модулей к реализации.

Источник переноса — единственный production-инстанс из `master` D-413. Commit исходника: `1636c2c4dabdd33420209cfd6617cc3c82fe2433` D-415. HEAD master не подменяет его автоматически.

## Назначение

Спроектировать новую версию MelodyTrack с полным описанием действующих и будущих возможностей, согласованными бизнес-правилами, моделью данных, доступом и дизайн-гайдом. Работающая версия остаётся источником сценариев и данных для будущего переноса.

По D-396 первое переключение требует воспроизведения необходимых повседневных сценариев старой системы. Пооперационный перечень составляется до переключения D-465. Обязательность возможности в общей спецификации не означает её включения в первый релиз.

По D-125 новая реализация разрабатывается с нуля сразу на целевом стеке без промежуточных реализаций для плавной смены технологий. Пользователь контролирует проектирование и разработку; перенос данных работающей версии рассматривается отдельно. Архитектурный набросок обсуждается, детали ещё уточняются.

По D-391 ассистент реализует бэкенд небольшими законченными порциями и останавливается после каждого шага для ручного ревью пользователем. Предметные правила согласуются до реализации. Фронтенд также проектирует и реализует ассистент. Полная офлайн-работа с редактором разрешения конфликтов выбрана D-449; протокол и макет ещё проектируются.

Исходная версия сохраняется для изучения и переноса. Rewrite — отдельная solution с C#-проектами, Npgsql/Dapper и SQL/C#-миграциями D-455. Уже есть модели/Rules, Application, первый блок хранения и импорта клиентов; HTTP-команды и остальные схемы ещё предстоят. Реализация и проверенность описываются отдельно в README rewrite.

## Статусы

- **Подтверждено** — пользователь явно определил требование или ответил на вопрос.
- **Наследуемая возможность** — функция присутствует в старой версии; её правила для v2 ещё нужно описать.
- **Направление из roadmap** — запланированная или ранее реализованная возможность; детали и место в v2 требуют обсуждения.
- **Предложение** — вариант проектирования, который ещё не выбран пользователем.
- **Открытый вопрос** — решение отсутствует; зависимая реализация не проектируется как окончательная.

Наличие текста в документе не меняет его статус на «подтверждено». Завершённая функция старой версии не считается автоматически завершённой функцией v2.

## Порядок проектирования

1. Описать пользователей, форматы работы и каталог возможностей.
2. Согласовать словарь, жизненные циклы и сквозные бизнес-правила.
3. Описать сценарии и права на действия и данные.
4. Разработать карту интерфейсов и дизайн-гайд на реальных сценариях.
5. Проверить сложные правила на конкретных примерах, включая офлайн и конкурирующие изменения.
6. Выбрать границу первого релиза и архитектуру, которая её обслуживает.
7. Описать модель данных, API и перенос существующих данных.
8. Начать реализацию по согласованным сценариям.
