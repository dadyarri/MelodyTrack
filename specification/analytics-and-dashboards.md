# Настраиваемые аналитические отчёты и дашборды

Статус: **направление подтверждено обсуждением пользователя 2026-11-16**; точные модели хранения, синтаксис языка, полномочия публикации, аудитории и граница релиза требуют отдельного утверждения. Это новая возможность F-012, не описание реализованного поведения.

## Назначение и границы

Предоставить возможность изменять состав аналитических дашбордов, запросы виджетов, их представления и видимость для ролей без правки SQL, изменения кода и выпуска новой версии приложения. Основной сценарий настройки — технический специалист/разработчик; заказчик не обязан самостоятельно пользоваться редактором. Пользователи дашбордов получают готовые представления.

Это расширение прежней границы D-229 («Конструктор виджетов не проектируется»). Подтверждённые содержательные блоки D-217/D-229, стартовые экраны D-216/D-246/D-247 и права D-424 сохраняются как требования к исходным конфигурациям и доступу, пока не изменены отдельно. Изменение конфигурации не меняет предметные формулы и правила из [финансов](finances.md).

**Не входит автоматически:** произвольный SQL, выполнение пользовательского кода, конструктор форм, изменение схемы БД, новые бизнес-функции без разработки, доступ клиентов к редактору, самостоятельное изменение дашбордов каждым сотрудником, полная BI-платформа или обязательное включение в первое переключение D-396.

## Объекты и жизненный цикл

- **Источник аналитики** — разрешённый логический набор данных, опубликованный сервером; не произвольная таблица БД.
- **Отчёт** — текст DSL, разобранная и проверенная модель запроса, параметры и один или несколько вариантов представления `вид`. Отчёт может переиспользоваться несколькими виджетами.
- **Виджет** — экземпляр отчёта на дашборде с выбранным видом, заголовком, параметрами, расположением и правилами видимости.
- **Дашборд** — упорядоченная конфигурация виджетов для заданной аудитории; может быть назначена стартовой странице соответствующей роли.
- **Черновик** и **опубликованная версия** — изменение редактируется и проверяется до публикации; пользователи видят только опубликованное. Предыдущая версия сохраняется для отката. Порядок управления версиями и конкретный объём аудита — предложение к согласованию.

Последовательность редактора (предложение): открыть конфигурацию, изменить DSL или состав виджетов, проверить синтаксис/типы/права, выполнить предпросмотр с явно указанным тестовым контекстом, опубликовать. Публикация активирует конфигурацию без рестарта и развёртывания приложения; открытые клиенты получают обновление по общей модели уведомления об изменениях [архитектуры](architecture.md), без фиксации транспорта.

Предварительная конфигурация должна воспроизводить утверждённые обзорные блоки: ресепшен администратора D-217, обзор занятий преподавателя D-246–D-247, состав показателей супера D-229. Обязательные рабочие действия не должны исчезать вследствие отсутствия аналитического виджета. Следует разделять рабочие блоки (список задач, быстрые действия, расписание) и агрегированные аналитические показатели: способность DSL заменить каждый рабочий блок **не подтверждена**.

## Доступ и аудитория

Видимость виджета задаётся по ролям (при необходимости — по эффективным разрешениям); конкретный механизм назначения — открытый вопрос. Пользователь может одновременно быть администратором/суперпользователем и преподавателем; эти признаки не исключают друг друга. Клиентам редактор DSL и конфигурации виджетов не предоставляется.

Видимость интерфейса **не является разрешением на чтение данных**. При каждом выполнении отчёта сервер применяет актуальные эффективные права (база роли + личные исключения D-447), область доступа к объектам и неизменяемые предметные ограничения [access.md](access.md). Настройка виджета, переменные, идентификаторы и агрегаты не могут расширить доступ. Преподавателям не открываются финансы школы, чужая свободная практика недоступна и суперу D-500. Администратор читает статистику и финансовые отчёты в установленных границах D-424/D-425. Неавторизованные поля и агрегаты недоступны через API, даже при прямом вызове без UI.

Право *редактировать и публиковать аналитическую конфигурацию* должно быть отдельным разрешением, а не следствием права видеть статистику. Кто получает это право по умолчанию, кто может менять видимость и можно ли делегировать публикацию — открытые вопросы. Требуются записи аудита автора, времени, версии и результата публикации; состав сохраняемого текста и правила отката уточняются.

## Компактный русскоязычный DSL

Подтверждено направление: краткие русские команды, нечувствительность ключевых слов и идентификаторов к регистру; строгая грамматика вместо свободной естественной речи. Следующий синтаксис — **проектная форма на основе примеров пользователя**, не окончательная грамматика:

```text
пусть период = 3 календарных месяца
пусть минимум = 0

из занятие
за $период
где преподаватель = @я и длительность > $минимум
группа по ученик ученик
взять
    сумма(длительность) минут,
    количество() занятий
сортировка по убыванию минут
лимит 20
вид таблица
вид столбцы(ученик, минут) "Активность учеников"
```

Команды ядра:

| Конструкция | Смысл |
| --- | --- |
| `из источник` | Разрешённый логический источник |
| `за период` | Временной фильтр по согласованному полю даты источника |
| `где условие` | Фильтр исходных записей |
| `группа по выражение [как] имя` | Ключ группировки и необязательный псевдоним |
| `взять выражение [как] имя, ...` | Поля результата и агрегаты |
| `сортировка по возрастанию/убыванию выражение` | Упорядочивание результата |
| `лимит N`, `лимит -N` | Первые/последние N строк после сортировки |
| `вид тип ["название"]` | Визуальное представление результата |
| `пусть имя = выражение` | Неизменяемая переменная в пределах отчёта |
| `$имя` | Обращение к переменной или параметру |
| `@я` | Ссылка на текущую пользовательскую идентичность |

Ключевое слово `как` необязательно, если псевдоним однозначно разбирается. Пробелы и переносы строк должны быть совместимы со списками после `взять`; точные правила разделения команд и зарезервированных слов — открытый вопрос. Парсер не должен угадывать намерение по морфологии произвольных названий полей. Строковые литералы сохраняют написание; правила сравнения строк в данных определяются отдельно от нечувствительности синтаксиса к регистру.

Нужно зафиксировать: (1) порядок операций и проверку использования агрегатов, (2) строгую типизацию сущностей и связей, (3) обработку двух учеников с одинаковым именем, (4) однозначный порядок при `лимит -N`. Предложение: отрицательный лимит выбирает последние N строк **с сохранением исходного порядка**, требует явной детерминированной сортировки.

### Даты и бизнес-календари

```text
за 30 дней
за 3 месяца
за 3 календарных месяца
за текущий месяц
за прошлый месяц
за 10 рабочих дней
```

`календарный` — модификатор выравнивания, а не отдельная единица времени. Предлагаемая семантика `3 календарных месяца`: текущий неполный календарный месяц и два предыдущих полных; обычные `3 месяца` — скользящий интервал. Для дней важно отдельно определить целые локальные даты либо точные 24-часовые интервалы; временную зону следует задавать по правилам источника/контекста, а не по часовому поясу сервера.

Лексер/парсер принимают известные словоформы единиц и модификаторов (например, `день/дня/дней`, `месяц/месяца/месяцев`, `год/года/лет`, `календарный/календарных/календарные`) без проверки грамматического согласования. Названия сущностей/полей не склоняются автоматически; каталог может регистрировать явные алиасы, редактор — предлагать подходящие формы.

**Предложение:** бизнес-календарь преподавателя учитывает индивидуальные регулярные выходные, отпуска, исключения, часы и исторические изменения. `за 10 рабочих дней` (отбор последних рабочих дат) и `где рабочий_день(дата, преподаватель)` (фильтр событий по датам) различаются. Способ задания календаря (`по календарю ...`), область доступных календарей, праздники и случаи отсутствия расписания требуют отдельного решения; существующая модель графиков/отпусков [scheduling.md](scheduling.md) — источник для анализа, не автоматическое подтверждение новой трактовки.

### Типизированные ссылки и параметры

`@я` обозначает текущего авторизованного пользователя, независимо от его сочетания ролей. Сравнение `преподаватель = @я` разрешается через явную предметную связь с учётной записью, без предположения, что роль определяет отдельный объект преподавателя. Несовместимый тип ссылки должен давать диагностируемую ошибку или определённый пустой результат; конкретное правило не утверждено.

`пусть` создаёт локальную неизменяемую переменную. **Предложение:** отдельное объявление `параметр` для значения, выбираемого через UI, с типом и значением по умолчанию. Запрещены произвольный исполняемый код, циклы, рекурсия и пользовательские функции.

Ссылки на конкретных учеников/преподавателей должны иметь стабильную идентичность независимо от переименования; исходный текст отчёта должен сохранять идентификаторы при экспорте/копировании. В редакторе допустимы человекочитаемые inline-бейджи с поиском и выбором объектов. Формат идентификаторного литерала и выбранный компонент редактора (Monaco decorations или CodeMirror widgets) пока **не утверждены**.

### Представления

Подтверждённая цель: `вид таблица`, `вид круговая`, `вид столбцы`, `вид линия` (набор может расширяться). Один отчёт может содержать несколько `вид` и выполняться для них один раз при совместимом наборе данных. Виджет выбирает одно из представлений отчёта. Для неоднозначного набора колонок задаются измерения/метрики (например, `вид столбцы(ученик, минут)`); точная грамматика опций, сериализация и состав поддерживаемых графиков требуют утверждения.

Таблица отображает типизированные колонки; круговая диаграмма требует категории и числовой показатель; столбцы и линия — измерение оси X, числовой показатель Y и необязательные серии. Недопустимые комбинации диагностируются до публикации. Нулевые значения, пропущенные временные корзины, «Прочее», единицы измерения и ограничения числа точек должны иметь согласованную семантику, а не зависеть случайно от библиотеки графиков.

## Редактор и эксплуатация

Предлагается редактор с подсветкой русского DSL, автодополнением по доступным источникам/полям/функциям, сообщениями об ошибках с позициями, вставкой ссылок по поиску и предпросмотром. Бейджи — только визуальное представление стабильных ссылок; текст DSL остаётся переносимым. Использование Monaco вместо CodeMirror не утверждено.

Изменение дашборда действует без SQL-миграции, релиза и перезапуска **в пределах уже опубликованного каталога источников/функций/видов**. Добавление нового источника, предметной функции или рендера может требовать изменения кода. Необходимо сохранить корректное поведение при ошибке данных/недоступности отчёта: виджет показывает собственную ошибку, не превращает ошибку в нулевую статистику и не ломает остальные виджеты.

Исполнение только серверное: allowlist источников и навигаций, проверка AST, параметризованные запросы, запрет произвольного SQL/DDL, лимиты строк, времени, вычислительной сложности и количества серий; все фильтры доступа применяются **до** агрегации, чтобы исключить утечки через `count()` и другие агрегаты. Предпросмотр не обходит права и не получает скрытые поля. При отмене/истечении времени запрос освобождает ресурсы. Кэширование возможно только с ключом, учитывающим полномочия и предметную область данных; общий кэш результатов разных пользователей по умолчанию небезопасен.

## Проверяемые сценарии и критерии приёмки

| ID | Сценарий / условие | Ожидаемый результат |
| --- | --- | --- |
| AN-01 | Изменить заголовок, запрос и расположение виджета в черновике | Опубликованная версия не меняется до публикации |
| AN-02 | Опубликовать валидную конфигурацию | Все соответствующие пользователи получают новый дашборд без релиза и перезагрузки сервера |
| AN-03 | Ошибка DSL, несовместимые типы или неподдерживаемое поле | Есть диагностика; некорректная версия не публикуется |
| AN-04 | Вернуть предыдущую опубликованную версию | Восстановлены её запросы, расположение и видимость; событие зафиксировано |
| AN-05 | Сотрудник не имеет права на показатель, но видит контейнер виджета | Сервер не отдаёт закрытые данные; прямой вызов API не обходит проверку |
| AN-06 | Два одноимённых ученика | Группировка по сущности не объединяет их; по имени — объединяет, если выбрана именно она |
| AN-07 | В отчёте несколько `вид` | Визуализации используют один согласованный набор данных и валидируются независимо |
| AN-08 | `за 3 календарных месяца` 16 ноября | При предложенной семантике включает данные с 1 сентября до текущего момента |
| AN-09 | `лимит -20` с сортировкой | Выбирает последние 20 записей и сохраняет порядок сортировки |
| AN-10 | `@я` для сотрудника с несколькими ролями | Идентичность пользователя не меняется от набора ролей; права на данные проверяются отдельно |
| AN-11 | Запрос превышает бюджет | Выполнение прерывается; остальные виджеты продолжают работать |
| AN-12 | Несуществующая/недоступная ссылка на объект в сохранённом отчёте | Есть предсказуемая диагностика, чужие данные не раскрываются |

## Открытые решения

1. Каким сотрудникам разрешены просмотр аналитики, создание черновиков, публикация и откат; нужны ли отдельные права на изменение видимости по ролям?
2. Возможна ли персональная компоновка дашборда пользователем или меняются только общие конфигурации? Нужны ли несколько дашбордов на роль/контекст?
3. Какие старые рабочие блоки допускается конфигурировать DSL, а какие остаются системными; как предотвращать исчезновение обязательных быстрых действий?
4. Полный каталог источников и бизнесовых функций, допустимые связи, правила видимости по данным и применение существующих календарей.
5. Каноническая грамматика `вид`, `пусть`, параметров, ссылок на объекты; семантика временных интервалов, сортировки и пустых значений.
6. Формат сохранения AST/текста, изменения схемы каталога и миграция опубликованных запросов при переименовании полей.
7. Офлайн-доступ к опубликованным результатам и доступность редактора с учётом D-449; стоимость выполнения и лимиты на сервере.
8. Дата реализации относительно первого переключения D-396; механизм проверки и миграции исходных дашбордов.
