# Вход, запомненные аккаунты и сессии

## Основные правила

D-420: токен доступа хранит сведения об идентичности пользователя, без роли и перечня прав. Сервер определяет доступные действия по актуальным данным пользователя и его индивидуальным политикам. Это не отменяет требования второго фактора и отзыва доступа. Право изменять разрешения принадлежит только суперу. По D-447 сервер учитывает актуальные разрешения глобальной роли и сохраняемые индивидуальные правки пользователя; изменения роли распространяются на всех её пользователей без потери этих правок.


Статус: способы входа, инвайты сотрудников, запоминание клиентов/сотрудников, переключение вкладок, обязательность второго фактора, права управления, выход/забывание и пути восстановления подтверждены. Access token действует пять минут; refresh token сотрудника — две недели с продлением при каждом успешном фоновом обновлении. Клиентский доступ действует до отзыва; отзыв и изменение прав применяются сразу. Настройки безопасности берут возможности текущего профиля с переработкой интерфейса. Подробные процедуры, форматы токенов, хранение и библиотеки ещё проектируются.

Связанные документы: [права](access.md), [дизайн-гайд](design-guide.md), [решения](decisions.md), [перенос](migration-and-acceptance.md).

Переключение сохранённых входов не создаёт семейный аккаунт или общий баланс. Парная встреча D-445 создаётся явно, с независимыми результатами клиентов. Денежный баланс и исторические финансовые факты принадлежат конкретному клиенту; новые абонементы не создаются D-450. Права определяются выбранной личностью и матрицей доступа, а не составом запомненного списка.

## Термины

Рабочая модель для обсуждения, не обязательный перечень таблиц БД.

| Понятие | Значение |
| --- | --- |
| Аккаунт | Личность для входа с ролью и разрешёнными связями |
| Клиентский кабинет | Собственные данные конкретного клиента, доступные его аккаунту |
| Сохранённый вход | Запомненная браузером запись ранее открытого кабинета/аккаунта; после истечения доступа остаётся с предупреждением, не давая сама по себе права работать с API |
| Сессия | Доступ аккаунта; у сотрудника обновление разрешено действующим refresh token, у клиентского кабинета разрешение действует до отзыва |
| Токен доступа к API | Краткоживущее разрешение запросов к API: пять минут, фоновое обновление; формат и хранение не выбраны |
| Refresh token сотрудника | Разрешение получать новый access token; действует две недели, срок сдвигается при каждом успешном фоновом обновлении; формат, ротация значения и хранение ещё проектируются |
| Активный аккаунт | Выбранная личность текущей работы, общая для вкладок браузера и определяющая права и область данных |
| Персональная ссылка | Способ первого/повторного клиентского входа; не идентификатор, автоматически разрешающий любые данные |
| Второй фактор | Код из приложения-аутентификатора или passkey при входе/выборе запомненного сотрудника; обязательность зависит от роли |
| Passkey | Способ второго фактора при парольном входе/выборе запомненного аккаунта; также заменяет пароль при первичном входе, но тогда при обязательном/включённом факторе требуется дополнительный код из аутентификатора |

Несколько сохранённых входов и несколько ролей одного аккаунта — разные задачи. Универсальный конструктор ролей и совмещение клиента/сотрудника не утверждены только из-за переключения аккаунтов.

## Вход клиента

Подтверждён способ по персональной ссылке, как в текущей версии. После входа кабинет можно запомнить в браузере. При последующем выборе запомненного кабинета повторная ссылка/PIN не нужны, пока доступ действителен. Клиентский доступ не имеет периодического срока истечения и сохраняется до отзыва D-096.

Администратор и суперпользователь могут выдавать, заменять и отзывать персональную ссылку D-091. Замена/отзыв прекращает ранее выданный по ней доступ на всех устройствах D-097: старая ссылка и ранее открытый кабинет больше не позволяют работать с API. Действующий access token не разрешает продолжать отозванный доступ. Для новой ссылки выполняется новый клиентский вход; принадлежность клиентской карточки не меняется.

Архивирование карточки также автоматически отзывает клиентский доступ на всех устройствах D-105. После разархивирования прежние ссылки/сессии остаются отозванными; для клиента выдаётся новая ссылка D-108. Сохранение самой карточки и её истории не возвращает разрешение входа. Правила архива — в [клиентах](clients.md).

Нужно определить:

- порядок выдачи новой ссылки и представление отозванного аккаунта в запомненном списке;
- сохранение клиентских ссылок при миграции;
- отдельное управление одним устройством, если оно потребуется; отзыв/замена ссылки уже подтверждены для всех устройств;
- поведение запомненной записи после отзыва; при истечении она сохраняется с предупреждением D-088;
- интерфейс выдачи/замены/отзыва ссылки; эти действия разрешены администратору и суперпользователю D-091.

Подтверждение «как сейчас» сохраняет способ входа. Точная криптографическая схема, пути URL и модель cookies старой реализации не объявляются выбранной архитектурой v2.

## Вход сотрудника и второй фактор

Сотрудник может входить по логину и паролю либо использовать passkey вместо пароля. Для суперпользователя и администратора второй фактор обязателен; это относится и к владельцу, и к разработчику с ролью суперпользователя. Преподаватель может включить второй фактор по желанию.

Второй фактор — код из приложения-аутентификатора или passkey. При парольном входе поддерживаются оба альтернативных способа. Если passkey заменяет пароль, после него требуется код из аутентификатора для сотрудника с обязательным или включённым вторым фактором D-084. Два последовательных запроса passkey не заменяют этот код.

| Сценарий | Подтверждение доступа |
| --- | --- |
| Вход по паролю, фактор обязателен или включён | Пароль, затем код из аутентификатора или passkey |
| Вход по passkey вместо пароля, фактор обязателен или включён | Passkey, затем код из аутентификатора |
| Вход преподавателя без второго фактора | Логин/пароль либо passkey вместо пароля |
| Выбор запомненного сотрудника, доступ действует, фактор обязателен или включён | Только код из аутентификатора или passkey; пароль не повторяется |
| Выбор запомненного преподавателя без второго фактора, доступ действует | Открывается сразу |

При выборе запомненного сотрудника с действующим доступом пароль повторно не запрашивается. Если второй фактор есть, сотрудник подтверждает его; без фактора аккаунт открывается сразу. Последний вариант относится к преподавателю без настроенного фактора: отсутствие настройки у администратора/суперпользователя не разрешает обход обязательного подтверждения. После истечения refresh token сотрудник повторяет полный вход: пароль или passkey D-093 с необходимым вторым фактором. Выбор истёкшего аккаунта не обходит повторный вход. Отдельный PIN для сотрудников не выбран.

У каждого сотрудника собственный аккаунт D-085, включая каждого администратора. Общая очередь задач не требует общей учётной записи. Только суперпользователь создаёт/блокирует аккаунты сотрудников и меняет роли D-090. Подключение сотрудника выполняется через одноразовое приглашение D-279; вид логина и второстепенные параметры приглашений ещё уточняются.

## Блокировка и уход преподавателя — D-284–D-285

Блокировка немедленно прекращает доступ D-098, D-284. Она не отменяет будущие занятия и не снимает назначения курсов. Суперпользователь видит предупреждение о будущих занятиях и отдельно организует замену. Нельзя откладывать отзыв доступа до разрешения конфликтов расписания.

Окончательный архив преподавателя требует заранее заменить его в будущих встречах и действующих сериях D-285. Исторические занятия, результаты и учебные назначения сохраняются. Переназначение в учебной механике отложено D-446 и не требует возобновлять курсы ради архива. Блокировка отзывает календарные подписки сотрудника D-290; архив клиента/замена ссылки — подписки на клиента. Архив не возвращает отозванный доступ.

## Приглашение и регистрация сотрудника — D-279

Суперпользователь создаёт одноразовую ссылку приглашения с ролью и передаёт её сотруднику внешними каналами. Автоматическая рассылка приложением не требуется. Сотрудник по ссылке регистрируется, самостоятельно задаёт пароль и настраивает 2FA/passkey в соответствии с ролью и D-082–D-084. Суперпользователь не задаёт временный пароль. При обязательной защите регистрационный сценарий включает её настройку до предоставления рабочего доступа. Использованное приглашение не позволяет зарегистрировать второй аккаунт.

Источники текущей схемы: [CreateInviteEndpoint.cs](../MelodyTrack.Backend/Api/Auth/Endpoints/CreateInviteEndpoint.cs), [RegisterEndpoint.cs](../MelodyTrack.Backend/Api/Auth/Endpoints/RegisterEndpoint.cs), [InviteRedirect.tsx](../MelodyTrack.Web/src/pages/invite-redirect/ui/InviteRedirect.tsx). Сейчас ссылка действует два дня, email может быть указан создателем или введён при регистрации; логин — email. Эти детали — сведения о текущей реализации, не отдельные подтверждённые настройки v2. В v2 приглашать может только суперпользователь D-090, даже если старый endpoint разрешает часть приглашений администратору. Открытая регистрация без приглашения не следует из сохранения этой схемы.

## Срок доступа и фоновое обновление

Refresh token сотрудника имеет скользящий срок две недели D-087, D-094. При каждом успешном фоновом обновлении access token окончание refresh token сдвигается на две недели вперёд D-095. Двухнедельного таймера отсутствия действий человека нет: открытая вкладка с работающим фоновым обновлением может поддерживать доступ без взаимодействия пользователя.

Access token действует пять минут и автоматически обновляется в фоне D-089. Для получения нового access token refresh token должен быть действительным D-094. Просроченный refresh token не может сначала продлиться и затем выдать access token. Формат токенов, хранение и ротация их значений не выбраны.

Если за две недели успешного обновления не было и refresh token истёк, появляется предупреждение и требуется повторный полный вход по паролю или passkey с необходимым вторым фактором. Запомненная сессия/аккаунт в браузере не очищается D-088: сотрудник видит прежнюю запись и может восстановить доступ к ней, а не добавлять аккаунт заново.

Пример: последнее успешное обновление 14 октября в 12:00 устанавливает окончание refresh token на 28 октября в 12:00. Успешное обновление 15 октября в 09:00 сдвигает окончание на 29 октября в 09:00. Если после первого обновления новых не было, 28 октября в 12:01 этот refresh token не выдаёт новый access token. Поведение точно на границе и использование access token, выданного до истечения refresh token, ещё описываются отдельно.

Это срок конкретного доступа сотрудника: продление активного аккаунта не утверждает автоматическое обновление всех неактивных запомненных аккаунтов. Клиентским кабинетам двухнедельное ограничение не применяется D-092; клиентское разрешение действует до отзыва D-096. Это не требует бессрочного access token: его пятиминутный срок остаётся отдельным правилом, механизм клиентского обновления ещё проектируется.

Истечение, явный выход, забывание аккаунта, отзыв клиентской ссылки и блокировка сотрудника — разные события. При обычном истечении запись сохраняется, но не разрешает API-запросы. По D-281 «Выйти» прекращает доступ выбранного аккаунта в текущем браузере, оставляя запись для повторного входа; другие аккаунты и другие устройства не затрагиваются. Клиенту для нового входа понадобится персональная ссылка, но сама ссылка не отзывается. «Забыть» также удаляет запись и доступно только на экране переключения D-282. Выход/забывание не должны оставлять действующий доступ этого аккаунта в другой вкладке того же браузера. «Выйти везде» — отдельная возможность текущего профиля сотрудника, сохраняемая по D-283.

Блокировка сотрудника и изменение прав применяются сразу D-098. Даже ещё действующий пятиминутный access token не разрешает заблокированному сотруднику работать или выполнять действие с прежними правами. Это функциональное требование к проверке доступа; оно пока не выбирает хранение токенов, запрос БД на каждый вызов или отдельный сервис сессий. Изменение прав само по себе не утверждает принудительный полный выход; интерфейс должен перейти к новым разрешениям.

Для отключённого устройства автономный доступ сохраняется до ближайшей синхронизации D-497. Это не продолжение серверного разрешения по устаревшему токену: при синхронизации все накопленные изменения проверяются по текущей матрице и при отсутствии доступа получают конфликт. Матрица прав не содержится в access token D-420 и не выводится из него.

## Восстановление и «Режим Бога»

Доступ сотрудника восстанавливается через суперпользователя. Если доступа нет у всех суперпользователей, используется «Режим Бога» D-086. Его инициализация выполняется только через прямой доступ к серверу по SSH: команда CLI генерирует одноразовую ссылку в веб-интерфейс D-500. Обычная роль супера не активирует этот режим. Конкретные сроки ссылки/сессии ещё проектируются.

Это сохраняет уже существующий аварийный путь v1. [Описание эксплуатации](../docs/unified-runtime-deployment.md) и [команда Init](../MelodyTrack.Init/README.md) описывают серверную выдачу короткоживущей одноразовой ссылки и отдельную аварийную сессию, независимую от обычных пользовательских паролей, факторов и сессий. Эти источники задают исходную модель для проектирования; порты, packaging и конкретные сроки старой реализации не утверждены для v2.

Подробная процедура ещё требует описания: подтверждение сотрудника, замена утраченных passkey/аутентификатора, повторная настройка обязательного фактора и судьба ранее выданного доступа. Состав остальных аварийных инструментов рассматривается отдельно.

По D-348 восстановление БД из резервной копии не требует массового сброса всех сессий и клиентских/календарных ссылок. Минимизируются сбросы без веской причины; при конкретной необходимости применяется адресный отзыв, насколько позволяет сохранившаяся информация. Требования немедленной блокировки/отзыва сохраняются. Потерянные при откате сведения об отзывах нельзя считать автоматически восстановленными; процедура ещё проектируется. Само восстановление БД не очищает запомненные аккаунты браузера. Подробнее — [эксплуатация и восстановление](migration-and-acceptance.md).

## Переключение и принадлежность данных

Предложения, основанные на аудите старой версии; конкретный интерфейс и механизм ещё не выбраны:

- Выбор сохранённого входа доступен из явного переключателя с понятным именем/ролью.
- Активная личность видна в интерфейсе, особенно при переходе из суперпользователя в клиентский кабинет.
- До показа данных другого аккаунта завершается переход контекста. Чужое содержимое не должно кратко оставаться на экране как данные нового аккаунта.
- Кеши, фильтры, черновики, отложенные команды и будущий офлайн сохраняют принадлежность аккаунту/клиенту.
- Несохранённая форма не отправляется от имени выбранного позже аккаунта; сценарий переключения объясняет судьбу черновика.
- Сервер проверяет действующее разрешение выбранного аккаунта при каждом действии; наличие его имени в запомненном списке не подменяет проверку доступа.
- Отозванный доступ даёт понятный путь повторного входа и не открывает прежний кеш как действующий кабинет.

Подтверждено D-080: одна активная личность для всех вкладок браузера. Переключение в одной вкладке меняет аккаунт в остальных, включая переходы между клиентом и сотрудником. Во всех вкладках показываются область данных и права выбранного аккаунта.

Подтверждённый сценарий D-280: пока второй фактор выбранного аккаунта не подтверждён, прежний остаётся активным. Отмена сохраняет прежний аккаунт; успешное подтверждение переключает все вкладки без повторного запроса того же фактора в каждой. Открытые формы сохраняют принадлежность прежнему аккаунту и не отправляются от имени нового. Судьба уже выполняющихся запросов и поведение скрытой/возобновлённой вкладки ещё требуют технического проектирования.

## Настройки безопасности — D-283

Исходный экран [ProfilePage.tsx](../MelodyTrack.Web/src/pages/profile/ui/ProfilePage.tsx) содержит смену пароля, подключение/подтверждение/отключение аутентификатора, список сеансов с текущим устройством, завершение одного сеанса и «Выйти везде». Эти сценарии сохраняются с ограничением обязательной защиты по роли. Управление passkey добавляется по D-079/D-083. Восстановление доступа — по D-086.

Компоновка перерабатывается: личные данные, доступность и безопасность разделяются; настройка пароля/фактора открывается по действию, основной экран показывает состояние защиты и понятные действия. Это рабочее предложение ассистента по D-223; точные макеты — в дальнейшем. Действие «Забыть» не относится к настройкам безопасности и доступно только при переключении аккаунтов D-282. См. [дизайн-гайд](design-guide.md).

## Управление объявлениями — D-294

Создание, редактирование и другие действия управления объявлениями доступны только через «Режим Бога» D-294 с инициализацией через SSH/CLI по D-500. Обычный супер не получает редактор объявлений по своей роли. Аудитории, дата/время окончания и настройка закрытия — D-472/D-477/D-490, включая совместимый показ до входа. Получение сообщения не является управлением им; режим не становится повседневной ролью.

## Уведомления и активный аккаунт — D-322–D-323, D-326

Push получает только текущий активный аккаунт D-322, общий для вкладок браузера. Сохранение других аккаунтов в списке не включает push от них на этом устройстве. Получение события не переключает аккаунт автоматически. Переключение и необходимые подтверждения по D-080/D-280 сохраняются.

По D-323/D-326 уведомления видны при действующей сессии. Допускаются системные push в фоне и на экране телефона с именем аккаунта и текстом события. Постоянная открытая вкладка не требуется; запомненное имя аккаунта без действующего доступа не заменяет сессию. Push добровольно включается для устройства D-293 и относится только к текущему аккаунту D-322. Конкретный механизм проверки сессии и доставки ещё проектируется.

## Предлагаемое упрощение

Разные способы входа клиентов и сотрудников могут вести к общей модели личности/действующего доступа и единой проверке прав. Это предложение к архитектуре, а не выбранная библиотека. Разделение кабинета и рабочего интерфейса само по себе не требует двух независимых систем сессий.

Школа одна D-001; настройка ролей и личных исключений описана в [правах](access.md), D-420/D-447/D-464. Доступ преподавателя к прогрессу задаётся назначениями курсов; статусы занятий он не меняет D-063. Эти предметные правила описаны в access.md.

## Источник текущего поведения

[Client portal sessions](../docs/client-portal-sessions.md) описывает нынешний вход по ссылке, одну возобновляемую личность на браузерный профиль и отсутствие сохранённого выбора. ## Уточнение технической модели — D-403/D-408/D-409

Выбрана собственная узкая схема аккаунтов с проверенными библиотечными компонентами пароля, TOTP и WebAuthn. Конкретные библиотеки, хранение и процедуры ещё выбираются. Push-подписка браузера/устройства имеет серверную привязку к текущему активному разрешённому аккаунту; переключение и отзыв обновляют привязку. Календарная подписка использует отдельный от входа отзываемый секрет, фиксированные владельца, субъект и состав данных, с зависимостью от актуального доступа. Ранее выбранные способы входа, фактор, сроки и немедленный отзыв не меняются.
